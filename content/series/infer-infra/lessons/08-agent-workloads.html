推理 Infra · 第 8 课 / 共 9 课

当请求变成任务

前七课每一课末尾都有一段「Agent 视角」。这一课把它们收拢起来，回答最开始的那个问题：以 agent 为主要负载之后，推理 infra 要多做什么。答案可以归成四条要求，每一条都对应引擎这一两年里新加的机制，也都需要 harness 这一侧配合。

图里的耗时沿用前几课的成本模型，是示意。引擎的功能、参数名和指标名对照了两个项目当前的 main 分支，其中不少是近期才加入的，行为可能还在变。

1 · 负载的形状

一个 agent 任务在引擎眼里是什么样

聊天负载的基本单位是请求：人打一句话，模型回一段话，结束。Agent 的基本单位是任务：harness 让模型决定下一步做什么，执行工具，把结果接到上下文后面，再问模型，循环几十上百次。引擎看到的是一串请求，但它们不是独立的。

聊天Agent
用户在意的单位一次回复整个任务
输入和输出的比例输入几百，输出几百输入几万，输出几百
相邻请求的关系下一轮可能几分钟后来，也可能不来下一步一定会来，而且开头和这一步完全相同
两次请求之间人在读、在打字工具在执行，短到几十毫秒，长到几分钟
到达方式大量用户各自随机到达，整体平滑工具一返回立刻发；派出子 agent 时一次来一批
取消偶尔经常：超时、打断、并行分支被剪掉
一次格式错误的代价用户重试一次整个任务可能失败

下图把一个任务摊在时间轴上。上半部分是这个任务占着多少 KV，下半部分是 GPU 在为它做什么。

预测默认参数下（30 步，系统提示 10K，每步新增 2K、输出 200），这个任务一共让模型读了多少 token，写了多少 token？

读了约 132 万，写了 6000，比例 220 ∶ 1。每一步都把到目前为止的全部历史重读一遍，所以输入是随步数平方增长的，这是第 3 课算过的账。

缓存全命中时，实际要算的输入只有 7 万，是 132 万的 5%。所以对 agent 来说前缀缓存不是一项优化，是成本能不能接受的前提。这也意味着：缓存一旦没命中，代价不是慢一点，是这一步的成本变成十倍以上。后面三节讲的都是怎么保住它。

再看最后一个数：默认每次工具执行 14 秒，这个任务有七成的时间在等工具。这段时间里它平均 5 GB 的 KV 留在显存里，没有任何请求在用。留着占地方，丢了下一步要重算。这就是第一条要求。

2 · 要求一

工具调用的间隙里，把 KV 留住

先回忆第 2、3 课：一个请求结束后，它的 KV 并不会立刻被清掉。vLLM 把这些块放回空闲队列，但保留哈希，谁需要新块时才从队列里取走、覆盖；SGLang 把它留在 radix tree 上，没有请求引用的叶子可以被淘汰。两边默认都按「最久没用的先淘汰」来选。

这套规则是为聊天设计的，隐含的假设是：越久没用的缓存，再被用到的可能性越低。Agent 打破了这个假设。一个在等慢工具的会话，它的 KV 已经 30 秒没人碰，按规则排在淘汰队列的前面；但它一定会回来，而且一回来就要全部用上。反过来，一个刚结束的一次性请求留下的 KV 很「新」，却多半不会再有人用。

引擎这边的应对有三类，下图逐个打开看效果。

  • 让淘汰顺序知道会话的存在。harness 告诉引擎哪些请求属于同一个还在进行的会话，淘汰时先淘汰不属于任何活跃会话的 KV。
  • 加一层更大更慢的缓存。GPU 上被淘汰的 KV 不直接丢，在主机内存里留一份，需要时拷回 GPU。拷回来比重算快得多。
  • 准入时避免无谓的淘汰。队列里同时有「前缀已在缓存里」和「要从头算」的请求时，先放前者进来，免得后者为了腾地方把前者马上要用的块挤掉。
预测把「一次性请求」从没有调到每秒 3 个。默认的 LRU 下，agent 会话的缓存命中会怎样？会话感知的淘汰呢？

两种都变差，但程度差得很远。默认参数下，LRU 的「整段重算」比例从 13% 涨到 63%，会话感知的从 9% 涨到 30%。

每个一次性请求结束时留下 6K token 的 KV，它们的「最近使用时间」比任何一个正在等工具的会话都新。LRU 分不清谁还会回来，于是为了给新请求腾地方，先淘汰了等得最久的会话，也就是工具最慢、上下文往往也最长的那些。会话感知的策略把不属于活跃会话的 KV 排在前面淘汰，这些一次性请求的残留成了缓冲。它仍然受影响，是因为一次性请求运行期间自己也要占显存，池子实际变小了。会话感知再加上主机内存层，重算才完全消失。

这说明 agent 流量和普通流量混跑在同一个引擎上时，默认策略会让前者替后者付出代价。要么分开部署，要么让引擎知道谁是谁。

两个引擎里对应的机制

  • SGLang 的会话感知 radix cache。启动时加 --enable-session-radix-cache，harness 在同一个会话的每个请求里带上相同的 session_id，会话结束时（包括出错和取消）调一次 /close_session。淘汰时先淘汰没有会话引用的节点。文档强调这是软保护，不是把内存钉住：只淘汰无引用的 KV 还不够时，有引用的也会被淘汰。
  • SGLang 的淘汰策略可选。--radix-eviction-policy 默认 lru，另有按命中次数的 lfu 和 slru、跟随请求优先级的 priority，以及文档标明面向 agent 和多轮负载的 tlru：它优先淘汰一段对话尾部「即使丢了，下次重算也不会超出 TTFT 预算」的那部分。
  • 分层缓存。SGLang 叫 HiCache（--enable-hierarchical-cache），三层：GPU 显存、主机内存、外部存储。前两层是单个实例私有的，第三层可以跨实例共享。vLLM 用 OffloadingConnector，把算好的 KV 块拷到主机内存（还可以再接更慢的层），命中时再提升回 GPU；文档说明拷贝和模型计算异步并行。
  • vLLM 的缓存感知准入。cache_aware_admission_window 设为 N 时，调度器在等待队列的前 N 个请求里，让前缀已在缓存里的先进，文档的说法是「免得一个冷请求把一个驻留请求还要用的块淘汰掉」。它只在 KV 池用到一半以上时才生效。另有 watermark 给池子留出一定比例的空闲块，减少反复淘汰和抢占。

作为对照，商业 API 的做法是把保留时间做成显式的约定：缓存按固定的存活时间计，在这段时间内命中就续期，超时才失效。开源引擎目前没有「保证留多久」的语义，留不留得住取决于那段时间里的显存压力，上面这些机制都是在改变压力来临时的淘汰顺序。

3 · 要求二

一批共享前缀的请求同时到达

主 agent 把任务拆开，同时派出 k 个子 agent。每个子 agent 的 prompt 是「父上下文 + 各自的一小段指令」。对引擎来说，这是 k 个几乎一模一样的长请求在同一瞬间到达。

它们能不能共享那段父上下文的 KV，取决于到达时这段前缀是否已经算完。前缀缓存只能复用已经存在的 KV；如果 k 个请求同时进来、前缀又不在缓存里，最坏情况下每个请求各算一遍。

第一种情况的浪费有两处：同一段前缀被算了 k 遍，还占了 k 份显存。避免它的办法两边都有：

  • 引擎侧：第 3 课提过，SGLang 的等待队列会把「和队列里别的请求共享前缀」的请求往后排，让一个先算，其余的等它算完再命中。这样即使同时到达，也会自动变成第二种情况。
  • harness 侧：通常父上下文刚被主 agent 的上一步用过，本来就在缓存里，天然是第三种情况。前提是子 agent 的 prompt 确实以父上下文原样开头。如果 harness 给子 agent 另外拼了一个系统提示、或者把父上下文做了摘要，前缀就对不上了。不确定的时候，先发一个，等它返回第一个 token 再发其余的。

扇出还带来两件事。一是优先级：子 agent 是后台工作，主 agent 的那一步有人在等。两个引擎都支持按优先级调度（vLLM 的 --scheduling-policy priority，SGLang 的 --enable-priority-scheduling），请求里带一个 priority 字段。二是取消：并行跑几个分支、取最先完成的那个，其余的要取消。第 4 课讲过取消要一到几轮才能把 KV 腾出来；harness 这边要做的是真的去断开连接，不要只是不再读它的输出。

4 · 要求三

上下文只往后加

第 3 课的结论是只有前缀能复用，从第一个不同的 token 起后面全部作废。Agent 循环里有几种常见的操作会在不经意间改动前面的内容：

  • 把思考内容从历史里去掉。带推理的模型每一步会先输出一段思考。不少 chat template 在下一轮拼 prompt 时会丢掉历史里的思考内容。这样一来，这一步生成时算好的 KV 里包含思考，下一步的 prompt 里没有，从这一步的回答开头起就对不上了，缓存只能命中到上一步的 prompt 末尾。支持交错思考（interleaved thinking）的模型把工具调用之间的思考留在上下文里，vLLM 文档里的示例就是把上一步的 reasoning 字段原样加回消息里再发。它多占上下文，但前缀是连续的。
  • 压缩历史。上下文快满时做一次摘要。第 3 课讲过，压缩点之后的缓存全部失效，那一步要重新 prefill 整段新上下文。压缩要做，但要把它当成一次有成本的操作来安排：保留系统提示和工具定义这段不动，压缩之后尽量长时间不再动。
  • 回头修改旧的工具结果。比如把早先一个很长的工具输出截短以节省空间。改的位置越靠前，作废的越多。
  • 按步骤增删工具。工具定义在最前面，一动全失效，还连带第 5 课说的语法编译缓存。

原则是只追加，不修改。必须改的时候，攒到一起一次改完。

5 · 要求四

按任务度量，而不是按请求

第 1 课定义的 TTFT、TPOT、吞吐都是按请求算的。它们仍然是诊断问题的基本工具，但用来回答「这套系统对 agent 好不好」会误导。第 7 课已经碰到一次：换路由策略让 TTFT 降了六成，任务总耗时只快了 5%。还有一个更隐蔽的效应：步数会放大尾延迟。

单步延迟的 P99 是指 100 步里最慢的那 1 步。一个请求碰上它的概率是 1%，听起来可以接受。但一个 50 步的任务里至少碰上一次的概率是 1 − 0.9950，接近四成。

所以对 agent 负载，单步的 P99 就是任务的日常，要看 P99.9 才是任务的尾部。而单步的尾部主要来自哪里，前面几节已经列过：缓存没命中的那一步、被抢占重算的那一步、语法第一次编译的那一步、适配器第一次加载的那一步。它们的共同点是偶发、代价是平时的十倍以上。

按请求看按任务看为什么换
TTFT、TPOT任务完成时间任务时间里还有工具执行和排队，单步快不等于任务快
每秒输出 token 数每小时完成的任务数输出 token 只占 agent 处理量的零头
单步 P99任务里最慢的一步；任务时长的 P95图 4

（通常不看）缓存命中率它是上面几项的共同原因，应当作为一等指标来监控和告警

原料从哪来

引擎不知道「任务」这个概念，它只看得到请求。任务级的指标要由 harness 或者网关按任务 ID 汇总，引擎提供原料：

  • 每个请求命中了多少。响应的 usage.prompt_tokens_details.cached_tokens。SGLang 要加 --enable-cache-report 才返回。把它除以 prompt_tokens 就是这一步的命中率，突然掉下去就是前缀被改了或者缓存被淘汰了。
  • 每个请求的时间构成。vLLM 加 --enable-per-request-metrics 后，响应里带排队时间、TTFT、生成时间、平均 token 间隔。
  • 引擎整体的缓存情况。vLLM 的 Prometheus 指标里有 vllm:prefix_cache_queries 和 vllm:prefix_cache_hits（相除得命中率）、vllm:kv_cache_usage_perc（池子用了多少）。
  • 缓存留了多久。vLLM 还有一组采样指标直接对应第 2 节的问题：vllm:kv_block_reuse_gap_seconds 是一个块两次被用到之间隔了多久，vllm:kv_block_idle_before_evict_seconds 是一个块从最后一次被用到被淘汰闲置了多久。前者的分布就是你的工具耗时分布；后者如果比前者短，说明缓存在会话回来之前就被淘汰了。
6 · 汇总

四条要求，两边各做什么

要求引擎和部署一侧harness 一侧相关的课
间隙里留住 KV够大的 KV 池（量化、少而大的副本）；会话感知的淘汰；主机内存和外部存储层；缓存感知的准入传会话标识，结束时关闭会话；慢工具尽量不要夹在任务中段2、3、6、7
共享前缀的并发队列内前缀去重；KV 按引用共享；优先级调度；快速取消子 agent 的 prompt 以父上下文原样开头；不确定时先发一个；取消时真的断开连接3、4
上下文只追加交错思考的支持；报告每个请求的命中量不改旧消息，不动工具定义；压缩攒到一起做；监控每步的命中率3、5
按任务度量暴露缓存命中、排队时间、KV 块寿命等指标按任务 ID 汇总时长、重算量、成功率；用任务级指标做容量规划和告警1、7、9

还有几条分散在前面各课、没有归进这四条的：

  • 工具调用默认没有语法约束，自己部署时在服务端统一打开（第 5 课）。
  • 路由要按前缀或会话做亲和，轮询在多副本下代价是成倍的（第 7 课）。
  • 前缀缓存命中之后，分词和模板渲染成了 TTFT 里不能忽略的一项，前端进程要给够 CPU（第 4 课）。
  • Agent 的输出重复度高，查表式的 speculative decoding 性价比好；跨请求的草稿语料库在多租户下要关掉（第 6 课）。

一个理解上的变化

把这些放在一起看，变化的核心是：KV cache 从一次请求内部的临时状态，变成了跨请求、跨分钟存在的会话状态。前七课里的显存管理、淘汰策略、路由、分层存储、度量，在聊天负载下都是「让缓存碰巧命中更多」的优化；在 agent 负载下，它们合起来是在管理一种有归属、有生命周期、丢了要付高价的状态。引擎这两年加的会话标识、会话感知淘汰、分层缓存、KV 传输，方向都是把这种状态显式地管起来。

7 · 对应到真实系统

文档入口和开关

vLLM

  • 缓存感知准入和水位：调度配置里的 cache_aware_admission_window、cache_aware_admission_threshold（默认 0.5）、watermark。定义和说明在 vllm/config/scheduler.py。
  • KV 卸载：文档 Features → KV Offloading Usage Guide。通过 --kv-transfer-config 配置 OffloadingConnector，默认是单层的主机内存，也可以配多层。单个请求可以用 kv_transfer_params.max_load_tokens 限制从卸载层取回多少。
  • 优先级调度：--scheduling-policy priority，请求里的 priority 数值越小越先处理。
  • 交错思考：文档 Features → Interleaved Thinking。
  • 指标：文档 Design → Metrics。按请求返回时间构成用 --enable-per-request-metrics；KV 块寿命采样用 --kv-cache-metrics-sample。

SGLang

  • 会话感知缓存：--enable-session-radix-cache，请求体里的 session_id，结束时 POST /close_session。文档 advanced_features/session_radix_cache。
  • 淘汰策略：--radix-eviction-policy（lru、lfu、slru、priority、tlru 等），参数用 --radix-eviction-policy-config 传。文档 advanced_features/radix_eviction_policy。
  • 分层缓存：--enable-hierarchical-cache、--hicache-ratio（主机内存池相对 GPU 池的倍数）、--hicache-storage-backend（第三层）。文档 advanced_features/hicache_best_practices。
  • 优先级调度：--enable-priority-scheduling。
  • 命中量上报：--enable-cache-report。

上线前对着查

  • 同一个任务连续两步，第二步的 cached_tokens 是否约等于第一步的 prompt_tokens 加上它的输出？不是的话，先查 harness 有没有改历史、模板有没有丢思考内容。
  • 工具耗时的分布是什么样的？最慢的那 5% 的工具跑完回来，缓存还在吗？
  • 子 agent 的 prompt 是不是以父上下文原样开头？
  • 多副本时，同一个会话的请求是否落在同一个副本？
  • agent 流量和一次性流量是否混在同一组引擎上？混的话有没有会话标识或优先级把它们区分开？
  • 监控里有没有任务完成时间和每任务重算 token 这两条线？
