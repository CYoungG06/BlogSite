跑一次，读懂曲线

前八课里所有的图都来自一个示意的成本模型：每轮固定 20 ms，每个序列 0.4 ms，每个 prefill token 0.1 ms。这一课把它换成你自己机器上的真实数字。配套有一套压测脚本，五组实验各对应前面的一课；跑完得到一个结果文件，贴进这个页面，就能看到你的曲线和对它的解读。

页面默认显示的是示例数据，来自一个按课程成本模型工作的假服务端，只用来说明曲线该怎么读，不代表任何真实硬件。压测脚本在这个假服务端上测通过，还没有在真实的 vLLM 或 SGLang 上跑过。

1 · 先想清楚

压测要回答的是哪个问题

「这台机器的性能怎么样」不是一个能回答的问题，因为答案随负载变。能回答的是下面三个，问法不同，做法也不同：

  • 最多能扛多少？不停地加压，直到吞吐不再上涨。得到的是容量。
  • 在某个流量下，用户感受到的延迟是多少？按固定的速率发请求，看延迟的分布。得到的是服务质量。
  • 改了一个配置，是变好还是变坏？同样的负载跑两遍，只改一个变量。

三个问题都要先定下负载的形状：prompt 多长、输出多长、请求之间有没有可复用的前缀、是均匀到达还是一批一批来。前八课反复出现的结论是，同一台机器在不同形状的负载下表现可以差一个量级。一个 512 进 128 出、互不相关的请求测出来的吞吐，对 agent 负载几乎没有参考价值。

闭环和开环

发请求有两种方式，测出来的东西不一样。

  • 闭环：固定 N 个并发，每个并发发完一个请求、等它完全返回，再发下一个。服务端变慢时，客户端发得也跟着变慢。它适合测容量：N 从小加到大，画出吞吐随并发的变化。
  • 开环：按固定的速率发请求（通常用泊松过程模拟随机到达），不管前面的有没有返回。服务端处理不过来时，请求会积压。它适合测某个流量下的真实延迟。

闭环有一个著名的陷阱：它测出的延迟偏乐观。线上的用户不会因为服务变慢就少来，闭环的客户端却会自动降速，于是排队的那部分时间永远测不到。所以容量用闭环测，延迟用开环测。

Agent 负载两者兼有：一个任务内部是闭环的（上一步返回了才有下一步），任务和任务之间是开环的（新任务随时到来）。脚本里的 agent 回放就是这样做的。

2 · 动手

在你的 GPU 上跑

脚本在本课同目录的 bench/ 下，说明见其中的 README.md。压测机只需要 Python 和 aiohttp。最短的流程是三步：

# 1. 启动服务端（以 vLLM 为例；--enable-prompt-tokens-details 让响应里带上缓存命中的 token 数）
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000 --max-model-len 32768 --enable-prompt-tokens-details

# 2. 跑完所有实验，约 15 到 20 分钟
cd bench
NOTE="vLLM, Qwen2.5-7B, 1x 80G" BASE_URL=http://localhost:8000 ./run_experiments.sh

# 3. 把 results/results.json 的内容贴到下面的框里

SGLang 对应的开关是 --enable-cache-report。有两张卡时，每张卡各起一个服务端，再设上 BASE_URL2，会多跑一组路由实验。

4 · 读图

几种典型的形状

  • 吞吐随并发先快后慢地涨，最后变平。快涨的那段是在摊薄每步的固定开销（第 1 课、第 6 课图 1）。变平说明每步的时间已经主要花在每个序列自己的计算上，再加并发只会让每个人更慢。变平之前突然掉头向下，通常是显存不够开始抢占了（第 2 课）。
  • 每个 token 的间隔随并发近似一条直线。截距和斜率就是你这台机器、这个模型的成本模型。截距大、斜率小，说明固定开销占主导，适合开大 batch；反过来说明已经接近计算上限。
  • 开环延迟随到达速率先缓后陡地涨。闭环测出的最高吞吐是在每个请求都很慢的状态下达到的，不能直接当容量用。给延迟定一个上限（比如不超过空载的 2 倍），对应的到达速率才是这种负载下可用的容量，通常明显低于最高吞吐。线上的目标流量留在它左边。
  • 冷请求的 TTFT 随 prompt 长度是一条直线，热请求的几乎是平的。两条线之间的距离就是前缀缓存省下的时间。热请求的线不平，说明缓存没有命中，先查服务端有没有开缓存、响应里的 cached_tokens 是多少。
  • agent 回放里，每一步的 TTFT 不随步数增长。这是前缀缓存在正常工作的标志。它一旦随步数上涨，回到第 8 课第 4 节查是什么改动了前缀。

常见的坑

  • 没有预热。服务端刚启动后的头几个请求会慢（缓存是空的、各种惰性初始化）。脚本每一档都丢掉了前 5 秒。
  • 所有并发同时起跑。大家一起 prefill、再一起 decode，步调一致，测出来的是这种人为同步的节奏。脚本让各个并发在预热期内错开启动。
  • 统计窗口比一个请求还短。高并发下一个请求要跑十几秒，窗口里可能一个完整的请求都没有。脚本会把每一档自动延长，直到有足够多的请求完成。
  • prompt 重复，意外命中缓存。用同一个 prompt 反复压测，测出来的是缓存的速度。脚本给每个 prompt 开头加了随机串。反过来，测 agent 负载时又必须让前缀真的能复用，否则测不出实际情况。
  • 输出长度不固定。模型自己决定什么时候停，每次长度不一样，吞吐就没法比。脚本用 max_tokens 加 ignore_eos 固定住。
  • 请求很长时按「完成了几个」算吞吐。高并发下一个请求要跑十几秒，统计窗口两头各切掉半个，结果严重偏低。脚本按每个请求在窗口内实际生成的 token 数算。
  • 压测客户端自己成了瓶颈。单进程的 Python 客户端每秒能处理的流式 chunk 是有限的。吞吐很高时换更高效的工具，或者开多个客户端进程。
  • 只看平均值。第 8 课讲过，对 agent 来说单步的 P99 就是任务的日常。
  • 一次改了两个变量。每次运行把启动命令记在 NOTE 里，结果文件会带上它。
5 · 继续

接下来可以自己验证的事

有了基线数据，前面每一课的结论都可以在你的机器上验证一遍。每一项都是「同样的负载跑两遍，只改一个开关」。

  • 工具间隙里缓存留不留得住（第 8 课）。python bench.py agent --gap 30 --bg-rate 2 --label lru，看命中率掉了多少。SGLang 上再加 --enable-session-radix-cache 启动服务端，压测加 --send-session-id，对比。
  • 量化（第 6 课）。换一个量化过的同款模型重跑实验 1。预期：低并发下每个 token 的间隔变短，高并发下差别不大；启动日志里的 KV cache 容量变大。
  • Speculative decoding（第 6 课）。加上 n-gram 推测重跑实验 1。预期：低并发有收益，高并发收益消失甚至变负。注意脚本用的是随机单词，输出几乎没有重复，n-gram 的接受率会很低；想看到真实的收益要换成有重复结构的 prompt。
  • CUDA graph 和编译（第 6 课）。vLLM 用 -O0 启动重跑实验 1，看低并发下截距变大了多少。
  • chunked prefill 和 token 预算（第 1 课）。调 --max-num-batched-tokens，一边跑实验 1 维持 decode 负载，一边发长 prompt，看 token 间隔的 P99。
  • 两个引擎对比。同一张卡、同一个模型，各跑一遍全套实验，用 OUT 分开存，分别贴进来看。
6 · 回顾

九课连起来

这门课从「一个 token 是怎么生成出来的」开始，一路讲到「几十步的 agent 任务对整套系统提出了什么要求」。中间每一课都在回答同一类问题：时间和显存花在了哪里，哪些是可以省的。

  • 第 1 课建立了成本模型和四个基本指标，说明了为什么要把请求合成 batch。
  • 第 2、3 课讲 KV cache：怎么分页存放，怎么跨请求复用。这是后面所有内容的地基。
  • 第 4 课把视野放大到整个服务进程，看 CPU 上的开销怎么拖累 GPU。
  • 第 5 课讲输出的正确性怎么保证，第 6 课讲几种加速手段各自动了成本的哪一项。
  • 第 7 课扩展到多卡多副本，问题变成了缓存在哪、请求该去哪。
  • 第 8 课把前面分散的 agent 视角收拢成四条要求。
  • 这一课把示意的数字换成真实的。

两个项目都在快速变化，这门课里的参数名和默认值会过时，机制本身过时得慢得多。以后看到一个新功能，可以先问它动的是成本模型里的哪一项、对缓存有什么影响、在什么负载下有效，大多数时候就能判断它值不值得用。
