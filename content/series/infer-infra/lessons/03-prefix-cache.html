算过的前缀不再算第二遍

第 1 课的 KV cache 只在一个请求内部复用。这一课把它推广到请求之间：两个请求开头相同的部分，KV 只算一次。对聊天这是一项优化，对 Agent 这是决定成本和延迟的头号因素。vLLM 和 SGLang 用两种不同的数据结构实现同一件事。

图里的块大小都用 4 个 token，方便看清。vLLM 默认是 16。

1 · 能复用的只有前缀

一个位置的 KV，取决于它之前的所有 token

回忆第 1 课的因果掩码：位置 i 的 K、V 是由第 0 到第 i 个 token 共同决定的，和后面的 token 无关。把这句话反过来读就是本课的全部依据：两个请求只要前 k 个 token 完全相同，它们前 k 个位置的 KV 就完全相同，第二个请求可以直接用第一个请求算好的结果，跳过这部分的 prefill。

这个性质有一个严格的限制：只对前缀成立。从第一个不同的 token 开始，后面每个位置的 KV 都变了，哪怕后面的文字一模一样。「两个请求里有一大段相同的内容」不够，这段内容必须从最开头起就相同。

预测题两个请求只有最开头的时间戳不同，后面一字不差。能命中多少？

零。选上面的「开头的时间戳变了」可以看到：后面每个 token 都标着 ＝，文字完全相同，但它们的 KV 是在「前面是 10:31」的条件下算出来的，对「前面是 10:32」的请求无效。

这是实际系统里最常见的缓存失效原因。系统提示里的当前时间、请求 ID、随机生成的示例顺序，只要出现在靠前的位置，就会让它后面的全部内容无法复用。

2 · vLLM 的做法

给每个写满的块算一个哈希

第 2 课里，KV 池被切成了物理块，每个块有引用计数。vLLM 的前缀缓存（Automatic Prefix Caching）在这个基础上只加了一样东西：块哈希。

  • 一个块写满后，算一个哈希值：hash(上一块的哈希, 本块的 token)。因为把上一块的哈希也算了进去，这个值实际上代表从序列开头到本块末尾的整段前缀。
  • 引擎维护一张表：哈希值 → 物理块。
  • 新请求到达时，先对 prompt 逐块算哈希，从第一块开始查表。命中就把那个物理块直接写进自己的块表、引用计数加 1；遇到第一个没命中的就停。
  • 请求结束后，它的块回到空闲队列，但哈希不清除。块处于「空闲，同时可被命中」的状态，直到它被重新分配给别人的那一刻才失效。

最后一条是关键设计：缓存不占用额外的显存预算。显存宽裕时缓存留得久，显存紧张时自动让位。

实现上还有两个细节值得知道：

  • 即使 prompt 的每一块都命中，引擎也要重算最后一个 token。命中只是拿到了 KV，而要采样下一个 token 需要最后一个位置的 logits，这必须真的跑一次 forward。
  • 哈希里除了 token，还会混入其他会影响 KV 的东西：用的是哪个 LoRA、多模态输入的内容，以及用户可以指定的 cache_salt。同样的文字在不同的 LoRA 下 KV 不同，不能混用。cache_salt 用来在租户之间隔离缓存，防止有人通过「我的请求是不是变快了」来探测别人发过什么。
预测题vLLM 的缓存块有没有过期时间？一个不再被使用的块能留多久？

没有过期时间。一个块能留多久，取决于它在空闲队列里前面还排着多少块，以及新请求消耗空闲块的速度。显存大、负载轻，可以留很久；负载一重，几秒内就被取走。

这对 Agent 的含义是：一步和下一步之间隔着工具执行的时间，这段时间里缓存能不能活下来，取决于同一台机器上别的请求有多忙，harness 自己控制不了。第 6 节的模拟器里有这个场景。

3 · SGLang 的做法

把所有见过的序列组织成一棵树

SGLang 的方案叫 RadixAttention。它不给块算哈希，而是把缓存里所有的 token 序列放进一棵 radix tree（基数树，一种压缩过的前缀树）：

  • 每个节点存一段 token，以及这段 token 的 KV 在池子里的位置。从根走到某个节点，路径上的 token 连起来就是一段被缓存的前缀。
  • 有共同前缀的序列共用同一段路径，到分叉点才分成不同的子节点。
  • 新请求到达时，从根开始沿着树逐个 token 比对。如果匹配停在某个节点的中间，就把这个节点分裂成两段，让分叉点正好落在节点边界上。
  • 正在运行的请求会给它路径上的每个节点加锁（引用计数）。淘汰时只能删没有被锁、也没有子节点的叶子，默认删最久没被访问的。

因为第 2 课讲过的按 token 寻址，树可以在任意一个 token 处分叉，复用不受块边界的限制。

缓存感知的调度

有了这棵树，调度器可以在请求还在排队时就知道它能命中多少。SGLang 提供了一组利用这个信息的排队策略，用 --schedule-policy 选择：

  • lpm（longest prefix match）：排队的请求按「能命中的前缀长度」从长到短处理。直觉是趁缓存还在，先把能用上它的请求跑完，免得缓存被无关请求挤掉后再回头重算。SGLang 论文证明了在一批请求离线处理的设定下，这个顺序等价于按树的深度优先顺序访问，命中率最优。
  • 当前的默认值是 fcfs（先来先服务）。lpm 需要对队列里每个请求做一次前缀匹配，队列超过 128 个请求时会自动退回先来先服务。
预测题队列里有三个请求：两个共享一段很长、但还没被缓存的前缀，第三个与它们无关。把三个一起送进同一批 prefill 有什么浪费？

那两个共享前缀的请求会同时 prefill，各自把相同的前缀完整算一遍。它们谁也用不上对方的结果，因为结果还没算出来。

更好的做法是先只放其中一个进去，另一个多等一轮，等前缀进了缓存再进，就只需要算它独有的部分。SGLang 的调度器里有这个逻辑：如果发现排队的请求之间共享着足够长的未缓存前缀，会把后来者暂时往后排。

这个场景在 Agent 里很常见：主 agent 同时派出几个子 agent，它们的 prompt 开头是同一份长长的上下文。

4 · 两种结构的对比

同一个性质，两种工程取舍

vLLM：块哈希SGLang：radix tree
复用粒度写满的整块，默认 16 个 token可以细到单个 token
查找方式对 prompt 逐块算链式哈希，查哈希表从根沿着树逐段比对 token
分叉点落在中间那一块不命中，整块重算节点分裂，命中到分叉点为止
没人用的缓存放哪留在空闲队列里，带着哈希留在树上，锁计数为 0
什么时候失效块被重新分配的那一刻显存不够时，淘汰最久未访问的叶子
调度是否感知缓存不感知，按到达顺序或优先级可选 lpm 等缓存感知策略
实现复杂度低，复用现有的块管理较高，需要维护树、锁和分裂

两者命中数的差别最多是一个块，对几千上万 token 的 prompt 来说通常可以忽略。真正拉开差距的是调度和淘汰策略：负载重、请求之间共享结构复杂（比如很多 agent 会话交错）时，谁的缓存先被淘汰、排队的请求按什么顺序进，对命中率的影响比粒度大得多。

5 · Agent 循环

没有前缀缓存，Agent 的成本按步数的平方增长

Agent 每走一步，发给模型的 prompt 都是「上一步的 prompt + 模型上一步的输出 + 工具返回的结果」。上下文只增不减，而且每一步都以上一步的全部内容为前缀。这是前缀缓存最理想的使用场景，也是最依赖它的场景：

  • 没有缓存：第 n 步要 prefill 全部 n 步的内容，N 步累计下来与 N² 成正比。
  • 缓存全部命中：每一步只 prefill 新增的那一小段，累计与 N 成正比。

下面的模拟器里，每根柱子是一步，高度是这一步的上下文长度，绿色是命中的部分，蓝色是真正要算的部分。试试几种会破坏缓存的情况。

Harness 这一侧该做什么

推理引擎只能复用相同的前缀，前缀是否相同由 harness 决定。几条通用的做法：

  • 稳定的放前面，易变的放后面。系统提示、工具定义在最前，然后是历史，最后是最新的输入。任何会变的东西（时间、用户状态）往后放，或者放进最新一条消息里。
  • 只追加，不改写历史。修改任何一条旧消息，它后面的全部内容都要重算。
  • 序列化要确定。工具定义的顺序、JSON 里 key 的顺序、空格和换行，两次请求之间必须逐字节一致。很多缓存不命中是因为一个字典的遍历顺序不固定。
  • 压缩历史是一次有代价的操作。压缩后系统提示部分仍然命中，但历史部分要重算。好处是上下文变短了。什么时候压缩是一个需要权衡的决定，不要每一步都做。
  • 看反馈。两个引擎都可以在返回的 usage 里报告这次命中了多少 token（cached_tokens）。调 harness 时盯着这个数最直接。
预测题Agent 跑到第 20 步，harness 为了省 token，从工具列表里删掉了一个用不上的工具。这一步的 prefill 量会怎样？

会暴涨到接近整个上下文。工具定义通常在 prompt 的最前面，改动它，后面的全部历史都失效。为了省几百个 token，重算了几万个。

想在中途限制模型能用哪些工具，更好的办法是保持工具定义不动，在后面追加一条说明，或者用下一课要讲的约束解码在输出端屏蔽它。

还没解决的问题。这一课默认所有请求都落在同一台机器上。生产环境通常有很多个副本，如果下一步请求被负载均衡器随机分到另一台机器，那台机器上没有这个会话的缓存，一切从头算起。所以多副本部署下，路由必须知道缓存在哪，这是第 7 课的内容。商业 API 提供的 prompt caching 也是同一个机制，把「命中的 token 更便宜」直接体现在计费上。
6 · 对应到真实系统

源码入口和开关

文件路径和默认值以当前 main 分支为准。

vLLM

  • V1 引擎里前缀缓存默认开启，可以用 --no-enable-prefix-caching 关掉。
  • 查找入口是 vllm/v1/core/kv_cache_manager.py 的 get_computed_blocks()，它调用 find_longest_cache_hit() 沿着请求的块哈希找最长的连续命中。
  • 命中长度上限是 prompt 长度减 1，对应「最后一个 token 必须重算」。
  • 块的 block_hash 字段、空闲队列里保留哈希的行为，在 kv_cache_utils.py 和 block_pool.py 里。
  • 文档里明确写着：它只减少 prefill 时间，不影响 decode。输出很长、输入很短的负载基本没有收益。

SGLang

  • 树在 python/sglang/srt/mem_cache/radix_cache.py：RadixCache 和 TreeNode。节点上有 key（token 段）、value（KV 下标）、lock_ref、last_access_time。
  • match_prefix() 做匹配，匹配停在节点中间时调 _split_node()。inc_lock_ref() / dec_lock_ref() 沿路径加锁和解锁。evict() 从可淘汰的叶子里按策略取，默认 LRU。
  • 排队策略在 managers/schedule_policy.py，缓存感知的有 lpm、dfs-weight 等，默认是 fcfs。
  • page size 大于 1 时，匹配长度会向下取整到 page 的整数倍，行为向 vLLM 的按块复用靠拢。
