推理 Infra · 第 7 课 / 共 9 课

一张卡不够之后

前六课都在一张 GPU、一个引擎里。这一课把范围放大到多张卡、多个引擎实例。要回答四个问题：一个模型怎么拆到多张卡上；有了多个副本之后请求该发给谁；为什么有人把 prefill 和 decode 拆到不同的机器上；一个基础模型怎么同时服务很多个微调版本。每一个都和前面讲过的 KV cache 直接相关。

图里的耗时沿用前几课的成本模型，是示意。参数名、默认值和文档说法对照了两个项目当前的 main 分支。

1 · 三种并行

拆模型，还是复制模型

手里有 8 张卡，有两类完全不同的用法，先分清目的。

模型一张卡放不下，就得把一个模型拆开，让几张卡合起来算同一个请求：

  • 张量并行（tensor parallelism，TP）。把每一层的权重矩阵都切成几份，每张卡拿一份。一个 token 经过每一层时，几张卡各算一部分，再把结果汇总。所以每一层都要在卡之间通信一次，需要卡间有高速互联。
  • 流水线并行（pipeline parallelism，PP）。按层的先后切：前一半的层放第一张卡，后一半放第二张卡，数据算完前半段传给下一张卡。一次前向只在交界处通信一次，对网络要求低，可以跨机器。

模型放得下，但一个引擎扛不住流量，就把整个模型复制几份，每份独立处理各自的请求。这叫数据并行（data parallelism，DP），每一份叫一个副本。第 4 课说过 vLLM 里每个副本是一个独立的 EngineCore 进程。

三者可以叠加。vLLM 文档给的选法是：单卡放得下就不拆；放不下但一台机器的卡够，用 TP；一台机器也不够，机器内 TP、机器间 PP。卡之间没有高速互联时（文档举的例子是 L40S），用 PP 代替 TP 通信开销更低。

下图是同样的 8 张卡在 TP 和 DP 之间的不同分法。注意看权重占了多少、留给 KV cache 多少。

预测8 张 24 GB 的卡跑 8B 模型。开 8 个独立副本，和 8 张卡合成一个 TP=8 的副本，哪种的 KV 总量大？

TP=8 的大，约 158 GB 对 53 GB，三倍。8 个副本把 15 GB 的权重复制了 8 份，占掉 120 GB；TP=8 只存一份。

但这不等于 TP=8 更好。8 个副本的吞吐接近单卡的 8 倍，互不干扰，坏一个还有 7 个。TP=8 每一层都要 8 张卡通信一次，加速远到不了 8 倍，一张卡出问题整个副本就停了。模型放得下单卡时，通常的做法是多副本；TP 是给放不下的模型用的。这道题要说明的是另一件事：副本越多，缓存被切得越碎。8 个副本就是 8 个互相看不见的前缀缓存，下一节的问题由此而来。

拆的是什么通信单个请求的延迟主要用途
张量并行 TP每一层的权重矩阵每层一次，要求高速互联能降，但不成比例单机内放下大模型
流水线并行 PP层的先后顺序每次前向只在交界处一次基本不降跨机器放下更大的模型
数据并行 DP不拆，整个复制副本之间不通信不变提高总吞吐

MoE（混合专家）模型还有一种专门针对专家层的并行方式（expert parallelism），常和 DP 组合使用，这时各副本的前向需要对齐，不再完全独立。这里不展开。

2 · 路由

请求发给哪个副本，决定了缓存能不能命中

有了多个副本，前面要加一个路由层（router，也叫网关或负载均衡器）决定每个请求去哪。传统 Web 服务的做法是轮询或者挑最闲的，因为请求之间互不相关，发给谁都一样。

LLM 服务不一样。第 3 课讲过，请求能跳过多少 prefill 取决于这个副本的 KV 池里有没有它的前缀，而每个副本的缓存是各管各的。Agent 的第 10 步如果被发到一个没见过前 9 步的副本，那一万多 token 的历史要从头算。vLLM 文档的原话：每个 DP 引擎有独立的 KV cache，把请求智能地导向合适的副本可以最大化前缀缓存的收益。

所以路由要同时考虑两件事，而且它们会打架：

  • 缓存亲和：同一个会话的请求尽量去同一个副本。
  • 负载均衡：别让某个副本堆积太多请求。

下图用同一组 agent 会话跑四种策略。每个会话有 4K token 的公共系统提示，每一步新增 1.5K 上下文，输出 150 个 token，两步之间有几秒的工具执行时间。

预测4 个副本、轮询。和「同一个会话永远去同一个副本」相比，每一步要重算的 prefill token 大约是几倍？

默认这组会话是 2.9 倍，看表里「重算的 prefill」一列：轮询 493K，按会话哈希 172K。理论上限是副本数 4。

亲和路由下，副本上留着这个会话上一步的全部 KV，每步只需要算新增的 1.5K。轮询下，一个会话的各步被轮流发到 4 个副本，某个副本上次见到它是大约 4 步之前，这中间几步的新增内容都得补算。副本越多，轮询浪费得越厉害。llm-d 项目的文档里给过一组实测对比：前缀感知路由相对轮询，输出吞吐 3 倍、TTFT 快 2 倍。

「按会话哈希」命中率最高，代价在最后一列之前那一列：各副本收到的请求数是 35 / 24 / 29 / 26，最多的比最少的多出近一半。哈希不看负载，碰巧几个长会话落在同一个副本就会挤，会话少或者长短悬殊时更明显。「缓存感知 + 负载保护」让出几个点的命中率，换来更均匀的分布。

还有一个值得注意的数：TTFT 降了六成，但每个会话的总耗时只快了 5% 左右。这组会话的时间主要花在 decode 和工具执行上。只看 TTFT 会高估路由的收益，第 8 课会回到「按任务而不是按请求度量」这件事。

真实的路由层怎么做

  • SGLang 的模型网关（一个 Rust 写的独立进程）默认策略就是 cache_aware。它不去问副本缓存里有什么，而是自己记账：为每个副本维护一棵近似的 radix tree，记录发给过它的请求文本。来一个新请求，先看负载是否失衡，判据是最忙和最闲的副本负载差超过 --balance-abs-threshold，并且比值超过 --balance-rel-threshold；失衡就发给最闲的。不失衡时找前缀匹配最长的副本，匹配比例超过 --cache-threshold 就发给它，否则发给树最小的那个，也就是缓存空间最宽裕的。树里存的是原始字符，不是 token，省掉了在路由层分词。
  • vLLM 内置的 DP 负载均衡（--data-parallel-size）目前只看每个引擎的运行队列和等待队列，文档明说还没有加入 KV cache 感知的逻辑。需要缓存感知时，把每个副本当成独立的 vLLM 实例，前面放外部路由。
  • 外部路由有 vLLM 自己的 production-stack（文档列了前缀感知路由），以及 llm-d。后者的做法不一样：读取 vLLM 上报的 KV cache 事件，维护一个全局索引，记录哪些 token 块在哪个副本上，属于「精确」而非「近似」的缓存感知。

路由层自己要高可用时还有一层问题。SGLang 文档提醒：部署多个网关实例时，各实例的 radix tree 不同步，同一个用户的请求可能经过不同的网关被导到不同的副本，预期缓存命中率会下降 10% 到 20%；在意的话，在网关前面再按用户 ID 做一致性哈希。

3 · Prefill 和 decode 分离

让长 prompt 不再打扰正在生成的请求

第 1 课讲过 prefill 和 decode 的性质相反：prefill 一次算很多 token，吃计算；decode 每步只算一个 token，但要很多步，对每一步的延迟敏感。放在同一个引擎里，一个长 prompt 进来，当前这几轮迭代都要带上它的 prefill，所有正在生成的请求的 token 间隔都被拉长。第 1 课的 chunked prefill 是把这次打扰切薄摊开，没有消除它。

PD 分离（prefill/decode disaggregation）把两个阶段放到不同的引擎实例上：

  1. 请求先到 prefill 实例，算完整个 prompt 的 KV。
  2. KV 通过网络传给 decode 实例。
  3. decode 实例拿到 KV，直接开始逐 token 生成并流式返回。

decode 实例上只有 decode，每一步的耗时稳定。代价是第 2 步：KV 很大。第 1 课算过 Llama-3.1-8B 每个 token 的 KV 是 128 KiB，32K token 的 prompt 就是 4 GB，要在几百毫秒内从一台机器搬到另一台，普通网络做不到，需要 RDMA 这类高速网络和专门的传输库。

预测做了 PD 分离，这个长请求自己的 TTFT 变快了吗？

默认参数下从 3.9 秒变成 3.7 秒，差不多。prompt 还是那么长，prefill 的计算量一点没少，还多了一段传 KV 的时间；快的那一点来自 prefill 实例不用同时照顾 64 个 decode 序列。把网络切到 10 Gb，传输要 3.4 秒，TTFT 反而比合并部署慢得多。

PD 分离改善的是别人：合并部署时已有的 64 个请求有将近 4 秒钟 token 间隔从 46 ms 涨到 250 ms，分离之后它们完全不受影响。vLLM 文档对这个功能有一句加粗的说明：它不提高吞吐。它的用处是分别调 TTFT 和 token 间隔，以及压住 token 间隔的长尾。

真实系统里

  • SGLang：同一个二进制用 --disaggregation-mode prefill 或 decode 启动成两种角色，传输后端用 --disaggregation-transfer-backend 选，支持 Mooncake（默认）和 NIXL。前面的网关用 --pd-disaggregation 模式，并且可以给两段分别设路由策略，文档的例子是 prefill 用 cache_aware、decode 用 power_of_two：prefill 那一侧才有前缀可复用，decode 那一侧只需要均衡。
  • vLLM：功能标注为实验性。跑两个 vLLM 实例，中间用一个 KV connector 传输，用 --kv-transfer-config 配置。文档列了 NixlConnector、MooncakeConnector、LMCache 等多种 connector。文档也承认 chunked prefill 调好分块大小能达到类似的效果，只是合适的值在实践中很难找，分离更可靠。
  • 同一套 connector 机制也用来把 KV 卸载到 CPU 内存或外部存储（vLLM 的 OffloadingConnector、LMCache）。原理相同：KV 是可以搬走、存起来、再搬回来的数据。第 8 课讲工具调用间隙的缓存保留时会用到。
4 · 多 LoRA

一份基础模型，挂很多个微调版本

LoRA 是一种微调方法：不改原来的权重矩阵 W，另外训练两个很窄的矩阵 A 和 B，用的时候按 W + BA 算。A 和 B 的宽度叫秩（rank），通常是 8 到 64，而 W 的边长是几千，所以一个 LoRA 适配器的体积通常不到基础模型的百分之一。

这给推理服务带来一种很划算的部署方式：显存里只放一份基础模型，同时加载几十个适配器，每个请求用 model 字段指定要哪一个。同一个 batch 里不同的序列可以用不同的适配器：大头的 W 那部分大家一起算，各自的 BA 那一小部分分别算再加上去。

它和前几课的交互

  • 前缀缓存按适配器隔离。KV 是由权重算出来的，权重不同 KV 就不同。两个请求系统提示完全一样，用的适配器不同，谁也复用不了谁的 KV。10 个适配器就是 10 套互不相通的前缀。
  • 一个 batch 里能混几个适配器有上限。vLLM 是 --max-loras，默认 1；SGLang 是 --max-loras-per-batch，默认 8。超过上限的请求要等下一轮，适配器种类多、流量分散时，这会变成排队延迟。
  • 适配器可以运行时加载和卸载。两边都有 load_lora_adapter 和 unload_lora_adapter 接口。显存里放不下所有适配器时按 LRU 换入换出，SGLang 里对应 lora_eviction_policy。冷的适配器第一次被用到要先加载，这是又一种首请求延迟。
  • 路由要多考虑一维。多副本时，请求最好去已经加载了它的适配器、并且缓存里有它前缀的副本。
预测一个 agent 系统给「规划」「写代码」「审查」三个角色各训了一个 LoRA，三个角色共用同一段 8K token 的系统提示。这段系统提示在 KV 池里占几份？

三份。三个适配器各算各的 KV，互不复用，8K 的公共前缀在显存里存了三遍，prefill 也算了三遍。

如果三个角色改用同一个基础模型、只靠不同的提示词区分，并且把角色说明放在公共系统提示的后面，这 8K 只存一份。要不要为每个角色训 LoRA，除了效果，还要把这笔缓存的账算进去。

5 · Agent 视角

分布式部署下，harness 能做什么

让路由层认得出会话。缓存感知路由靠前缀匹配能自动把同一个会话导回同一个副本，但前提是 prompt 的前缀稳定（第 3 课）。如果用的是只支持按键哈希的普通负载均衡器，harness 要在每个请求里带一个稳定的会话标识（请求头或 user 字段），让它有东西可哈希。

子 agent 扇出时，亲和和均衡的矛盾最尖锐。主 agent 一次派出 10 个子 agent，它们共享同一大段父上下文。全发给同一个副本，前缀只算一次，但那个副本瞬间多了 10 个并发；分散开，每个副本都要把父上下文重算一遍。图 2 的「缓存感知 + 负载保护」处理的就是这种情况：先亲和，负载差超过阈值再分流。阈值怎么设，取决于前缀有多长、重算有多贵。

副本数不是越多越好。图 1 的结论：同样的卡，副本越多，每个副本的 KV 池越小，缓存越碎。长上下文的 agent 负载下，少一些、大一些的副本可能比多一些、小一些的副本总体更省。

PD 分离和多轮会话配合要留意。下一步的 prefill 要用到上一步的 KV，包括上一步在 decode 实例上生成的那部分。prefill 实例上有没有这些 KV、要不要再传一次，取决于具体的实现和配置。部署前用真实的多轮负载测缓存命中率，不要只测单轮。

6 · 对应到真实系统

文档入口和开关

vLLM

  • 并行：--tensor-parallel-size、--pipeline-parallel-size、--data-parallel-size。文档 Serving → Parallelism and Scaling、Data Parallel Deployment。
  • 启动日志里的 GPU KV cache size: … tokens 和 Maximum concurrency for … tokens per request 两行，就是图 1 算的那两个数，是判断卡够不够的第一手依据。
  • 内置 DP 负载均衡在 API server 进程里，按各引擎的运行和等待队列分配。--max-num-seqs 是每个副本各自的上限。
  • PD 分离：文档 Features → Disaggregated Prefilling（实验性）。配置项 --kv-transfer-config。
  • LoRA：--enable-lora、--lora-modules 名字=路径、--max-loras（一个 batch 里最多几个，默认 1）、--max-lora-rank（默认 16）、--max-cpu-loras。运行时加载要设环境变量 VLLM_ALLOW_RUNTIME_LORA_UPDATING=True。
  • 外部路由和编排：文档 Deployment → Integrations 下的 production-stack、llm-d 等。

SGLang

  • 并行：--tp-size、--pp-size、--dp-size（也接受和 vLLM 同名的长参数）。
  • 网关：仓库里的 sgl-model-gateway/，策略实现在 src/policies/，cache_aware.rs 开头有一段完整的算法说明。策略用 --policy 选：random、round_robin、power_of_two、cache_aware（默认）、bucket。
  • 缓存感知的调节项：--cache-threshold（默认 0.3）、--balance-abs-threshold（默认 64）、--balance-rel-threshold（默认 1.5）。
  • PD 分离：--disaggregation-mode、--disaggregation-transfer-backend；网关侧 --pd-disaggregation、--prefill-policy、--decode-policy。文档 advanced_features/pd_disaggregation。
  • LoRA：--enable-lora、--lora-paths、--max-loras-per-batch（默认 8）、--max-lora-rank、--lora-target-modules。文档 advanced_features/lora。
