推理 Infra · 第 6 课 / 共 9 课

每种加速手段，省的是哪一项

量化、speculative decoding、CUDA graph、编译、更快的注意力算子，名字很多，常被混在一起说「能加速」。这一课把一步 decode 的时间拆成几项，逐个对上：每种手段动的是哪一项，在什么负载下有用，在什么负载下没用甚至更慢。

图里的耗时是示意模型，沿用第 1 课的成本模型并把它拆开。引擎的参数名、默认值和文档说法对照了两个项目当前的 main 分支；这些功能迭代很快，选型前请以当时的文档为准。

1 · 先拆账

一步 decode 的时间由三项组成

第 1 课给过一个成本模型：一次前向的固定开销 20 ms，每多一个 decode 序列加 0.4 ms。那个 20 ms 里其实有两样性质完全不同的东西，这一课要把它拆开。

  • 读一遍权重。每生成一个 token，每一层的权重矩阵都要从显存里读出来参与一次运算。8B 参数的模型用 16 位浮点存是 16 GB。GPU 每秒能从显存读多少字节是有上限的，叫显存带宽，A100 80GB 的标称值是 2,039 GB/s。16 GB ÷ 2,039 GB/s ≈ 8 ms，这是读一遍权重的时间下限。第 1 课说 decode「受显存带宽限制」指的就是它。
  • 框架和启动开销。一次前向由成百上千个小的 GPU 运算组成，每个都要由 CPU 上的 Python 和 PyTorch 代码发起。发起本身要时间，和模型算了多少没关系。
  • 每个序列自己的计算。每个序列要读自己的 KV cache、做自己的那一行矩阵运算。这一项和 batch 大小成正比。

关键在于前两项是一个 batch 里所有序列共摊的：权重只读一遍，大家一起用。所以 batch 小的时候它们占大头，batch 大的时候第三项占大头。下面每种手段只动其中一项，这就决定了它在哪种负载下有效。

预测把权重从 16 位量化到 4 位。只有 1 个序列时 TPOT 降多少？256 个序列时呢？

1 个序列时从 20.4 ms 降到 14.4 ms，少了 29%。256 个序列时从 122.4 ms 降到 116.4 ms，只少 5%。

省掉的都是那 6 ms 的读权重时间。batch 小的时候它占一步的三成，batch 大了之后一步的时间主要花在每个序列自己的计算上，那一项量化没有动。所以「量化能加速」这句话要带上条件：并发低的时候明显，并发高的时候主要收益不在速度上，在第 2 节要讲的显存上。

2 · 量化

每个数少占几位

模型权重默认用 16 位浮点数存（FP16 或 BF16）。量化是用更少的位数表示它们：8 位或 4 位。常见的写法是 W4A16 这种形式：W 后面是权重的位数，A 后面是激活值的位数。激活值指每一层算出来、传给下一层的中间结果，它们不存盘，每次前向现算。

  • 只量化权重（W4A16、W8A16）。权重按 4 位或 8 位存，用的时候还原成 16 位再算。省的是存储和读取；计算本身还是 16 位的。GPTQ、AWQ 这两种常见方法产出的就是这类模型。它们需要先拿一批校准数据跑一遍，决定每一层怎么舍入损失最小，所以是离线做好再加载。
  • 权重和激活都量化（W8A8，常见的是 FP8）。连计算也在 8 位上做，需要硬件和算子支持。可以离线做，也可以加载时现转。
  • KV cache 量化。和上面两种无关，量化的是第 2 课那个 KV 池子里存的数，从 16 位变成 FP8，同样的显存能放两倍的 token。

量化省下的显存去了哪，是它对推理服务最重要的影响。第 2 课说过，显存里除了权重，剩下的几乎全给 KV cache。权重占得少，KV 池子就大。

预测24 GB 的卡跑 8B 模型。权重从 16 位量化到 4 位，KV 池能放的 token 数变成原来的几倍？

约 2.7 倍，从 5.4 万个 token 到 14.6 万个。权重从 15 GB 降到 3.7 GB，省出来的 11 GB 全部进了 KV 池，池子从 6.6 GB 变成 17.9 GB。

对 Agent 负载，这比 TPOT 上那几毫秒重要。第 3 课讲过，工具调用的间隙里前缀留在缓存里靠的是池子够大；池子大 2.7 倍，同样的并发下被淘汰的前缀少得多。再把 KV 也换成 FP8，容量再翻一倍。

几个容易想当然的地方

  • 只量化权重，高并发下不会更快。图 1 已经看到了。权重在用之前要还原成 16 位，计算量没有少。vLLM 文档里写明它的权重量化算子（Marlin）始终用 16 位激活值运行。
  • 标的方案和实际跑的方案可能不一样。一个标着 W8A8 的模型，如果当前设备上没有能跑 8 位激活的算子，vLLM 默认会退回到只量化权重的算子，按 W8A16 跑，并打一条警告。精度不受影响，但速度和这个模型发布时的基准测试不是一回事。设 VLLM_STRICT_QUANT_SCHEME=1 可以禁止这种回退。
  • 精度损失要在自己的任务上测。8 位通常损失很小，4 位在小模型上更明显，但都因模型和任务而异。SGLang 文档的原话是量化后的模型必须重新跑基准验证。对 Agent 要测的是任务成功率和工具调用的合法率：第 5 课算过，单次合法率掉一个百分点，50 步的任务成功率会掉很多。
3 · Speculative decoding

让大模型一步确认好几个 token

decode 慢的根源是串行：生成 100 个 token 就要跑 100 次前向，每次都要把权重读一遍。但第 1 课也说过，prefill 可以一次前向并行处理很多个位置。Speculative decoding（推测解码）利用的就是这个不对称：

  1. 用一个便宜的办法先猜接下来的 K 个 token，叫草稿。
  2. 大模型（目标模型）做一次前向，像 prefill 那样同时处理这 K 个位置，得到它自己在每个位置上的概率分布。
  3. 从左到右检查草稿：和目标模型的意见相符就接受，遇到第一个不接受的，用目标模型自己的分布重新采一个，后面的草稿全部丢弃。

猜对了几个，这一次前向就白赚几个 token。猜错了也不亏正确性：被拒绝的位置上目标模型本来就算出了自己的分布。

接受的规则是精心设计过的。设草稿在某个位置给它选的 token 的概率是 q，目标模型给同一个 token 的概率是 p。p ≥ q 就直接接受；p < q 时以 p/q 的概率接受。被拒绝时，从「p 减 q 的正的部分」重新归一化得到的分布里采样。可以证明这样得到的输出分布和只用目标模型逐个采样完全相同，所以它是无损的，只换速度，不换质量。

预测第 4 个草稿 token 被拒绝了。第 5 个草稿 token「的」目标模型也算过了，为什么不能留着用？

因为它是接在「数字」后面猜的，目标模型验证它时看到的上文也是「数字」。现在第 4 个位置换成了「元素」，第 5 个位置的上文变了，之前算的概率和 KV 都作废。

这一轮的结果是：一次目标前向处理了 5 个位置，产出 4 个 token（3 个接受的草稿，加 1 个重新采样的）。被丢弃的位置对应的 KV 也要从块里退掉，这是第 2 课的块管理要配合的地方。

划不划算，取决于两个数和当前的并发

设每个草稿 token 被接受的概率是 α，每轮猜 K 个。Leviathan 等人的论文给出每轮期望产出的 token 数是 (1 − αK+1) / (1 − α)。α = 0.7、K = 4 时是 2.8 个。

成本有两块。一是出草稿的成本，每个草稿 token 花目标模型一步的 c 倍时间。二是验证的成本：目标模型这一步要多处理 K 个位置。并发低的时候 GPU 的计算能力有富余（时间花在读权重上），多算几个位置几乎不要钱。并发高的时候 GPU 已经在满负荷计算，每个序列多 K 个位置就是实打实的多 K 份计算量。

预测默认参数（α = 0.6，K = 5，c = 0.05）。并发从 1 涨到 512，加速比怎么变？

从 1.9 倍一路降到 1.0，在 512 附近变成不赚不亏。再把 α 调到 0.4，并发过了 25 左右就低于 1，开着比不开还慢。

vLLM 文档对这个功能的定位就是「在中低 QPS、受显存带宽限制的负载下降低 token 间隔」，并提醒：GPU 不再受显存带宽限制之后，验证每个草稿位置都要花计算量，高并发下可能比不开更慢。所以它是一个延迟优化，不是吞吐优化。负载波动大的服务需要能按当前并发动态减少或关掉推测，两个引擎都有这类自适应的选项。

草稿从哪来

草稿来源出草稿的成本适合
草稿模型一个同系列的小模型，比如 8B 配 0.6B中。要多占一份权重和 KV 的显存通用
EAGLE、MTP 一类接在目标模型上的一个小预测头，利用目标模型内部的中间结果（hidden states）来猜低。但要有针对该模型训练好的头通用，两个引擎文档里都列为收益最高的一类
n-gram不用模型。看最近输出的几个 token 在 prompt 里出现过没有，出现过就把它后面那一段抄来当草稿几乎为零输出大量重复输入的任务：改代码、摘抄、改写
Suffix decodingn-gram 的扩展。除了本请求的 prompt 和输出，还去匹配之前其他请求的输出，并按出现频率选最可能的续写几乎为零重复度高的负载。vLLM 文档点名了代码编辑和 agent 循环
4 · 图捕获、编译和算子

把「发起运算」本身的开销压下去

图 1 里灰色的那一项和模型算了什么无关，是把运算发起出去的成本。这一类优化对用户是透明的，引擎默认就开着，需要知道的是它们各自在做什么、代价是什么。

CUDA graph：把一次前向录下来重放

正常执行时，一次前向里的每个 GPU 运算都由 Python 代码逐个发起：准备参数、调用驱动、提交给 GPU。模型小、batch 小的时候，GPU 算一个运算的时间可能比 CPU 发起它的时间还短，GPU 在等 CPU。CUDA graph 是 CUDA 提供的一种机制：把一整串运算的调用录成一张图，之后每次只需一次调用就能把整张图重放一遍。

录下来的图形状是固定的，所以有三个后果：

  • 引擎要在启动时为一组 batch 大小各录一张图，这是启动变慢、多占一些显存的原因之一。运行时遇到没录过的大小，就补齐到最近的一个录过的大小。
  • 形状规整的 batch 最容易录。vLLM 把「所有请求都只算 1 个 token」的纯 decode batch 单独对待，为它录整张图；含 prefill 的 batch 形状多变，只录注意力之外的部分，注意力照常逐次发起。这个默认模式叫 FULL_AND_PIECEWISE。
  • 文档说这种设置对小模型的低延迟场景收益最大，同时占显存最多、启动时录制最久。

编译：把相邻的小运算合成大的

torch.compile 会先把模型的前向过程追踪成一张计算图，再生成更紧凑的代码，比如把相邻的几个逐元素运算合成一个 GPU 运算（融合），省掉中间结果的读写。vLLM 里它默认开启，并且有一条约束值得记住：所有编译都在开始服务之前完成，不会有哪个请求触发新的编译，否则那个请求的延迟会突然变得很长。编译产物缓存在 ~/.cache/vllm/torch_compile_cache，可以整个目录拷到部署环境里省掉启动时的编译。

vLLM 用 -O0 到 -O3 四个等级打包这些开关：-O0 不编译、不录图，启动最快，适合调试；-O2 是默认，也是文档推荐的生产配置。SGLang 的 CUDA graph 同样默认开启，用 --cuda-graph-config 一类的参数配置；它的 --enable-torch-compile 在文档里标注为不再维护。

注意力算子

注意力是前向里最特殊的一个运算：它要去读 KV cache，而第 2 课讲过 KV 是按块表分散存放的。通用的矩阵运算库不认识块表，所以两个引擎都依赖专门为推理写的注意力算子库（FlashAttention、FlashInfer 等），并允许用 --attention-backend 选择。SGLang 还可以给 prefill 和 decode 分别指定。不同的算子库对 CUDA graph、FP8 KV cache、speculative decoding 的支持程度不同，这是「某两个功能不能同时开」这类限制的常见来源。

5 · 对照表

谁省在哪

手段动的是哪一项主要改善代价和失效条件
权重量化每步要读的字节数；权重占的显存低并发下的 TPOT；KV 池容量精度。只量化权重时，高并发下不变快
KV cache 量化每个 token 的 KV 占用并发数、能保留的前缀精度。依赖注意力算子支持
Speculative decoding每个 token 平均要跑几步大模型中低并发下的 TPOT高并发下可能更慢；草稿模型占显存；接受率因任务而异
CUDA graph每步发起运算的 CPU 开销小模型、小 batch 的每步固定开销启动时间和显存
编译和融合运算之间的衔接开销每步固定开销启动时的编译时间，可以缓存
前缀缓存（第 3 课）prefill 要算的 token 数TTFT只对相同前缀有效，不影响 decode

把前缀缓存也放进来，是因为这张表给出了一个完整的分工：前缀缓存管 prefill，这一课的手段主要管 decode 和显存。一个请求的延迟是 TTFT 加上输出 token 数乘以 TPOT，先看清哪一段长，再决定用哪一种。

6 · Agent 视角

Agent 负载下怎么选

缓存命中之后，剩下的时间主要在 decode。Agent 的请求输入长、输出短，看上去是 prefill 重的负载。但第 3 课之后，命中缓存的那一步 prefill 只算新增的几千个 token，几百毫秒；输出 200 个 token 的工具调用，按每步 20 多毫秒算也要好几秒。所以前缀缓存做好之后，下一个值得优化的就是 TPOT。

Agent 的输出重复度高，查表式的草稿特别合适。改代码时大段照抄原文件，工具调用的 JSON 骨架每次都一样，同一个任务的多个子 agent 输出相似的内容。n-gram 和 suffix decoding 在这类输出上接受率高，又不占显存、不需要额外的模型。

跨请求的草稿是一条旁路。Suffix decoding 的语料库存的是所有请求的输出。vLLM 文档专门提醒：草稿不会改变输出内容，但被接受了多少会体现在生成速度上，所以一个请求能从速度上间接感知别的请求输出过什么。多租户、请求之间必须互不影响的服务，要把这个语料库关掉（suffix_decoding_corpus_tokens: 0）。

量化对 Agent 的主要价值是显存。图 2 的结论。更大的 KV 池意味着工具调用间隙里前缀更不容易被淘汰，也意味着能同时挂住更多长上下文的会话。

和约束解码一起用时要查兼容性。第 5 课讲过，自动机每一步都要推进状态。Speculative decoding 一次试走好几步、还可能退回，自动机就得支持回退。两个功能能不能同时开、开了之后重叠调度还在不在，取决于具体的算法组合，上线前要对照文档确认。

7 · 对应到真实系统

文档入口和开关

这一课的内容主要落在配置上，所以列的是文档和参数。路径以当前 main 分支为准。

vLLM

  • 量化：文档 Features → Quantization。预先量化好的模型直接加载；也可以用 --quantization fp8_per_tensor 这类参数在加载时现转。官方配套的量化工具是 LLM Compressor，支持 FP8 W8A8、INT8 W8A8、INT4 W4A16 等方案。
  • KV cache 量化：--kv-cache-dtype fp8。可以用 --kv-cache-dtype-skip-layers 让个别层保持原精度。
  • Speculative decoding：文档 Features → Speculative Decoding。用一个 JSON 配置，例如 --speculative-config '{"method": "ngram", "num_speculative_tokens": 5, "prompt_lookup_max": 4}'。method 常见取值有 draft_model、ngram、suffix、mtp、eagle3。
  • CUDA graph 和编译：文档 Design → CUDA Graphs、torch.compile integration、Optimization Levels。开关是 -O0 到 -O3，细调用 --compilation-config。
  • 注意力算子：文档 Design → Attention Backend Feature Support 有一张自动生成的支持矩阵。开关是 --attention-backend。

SGLang

  • 量化：文档 advanced_features/quantization。AWQ、GPTQ 这类离线量化的模型直接加载，不要再加 --quantization；这个参数是给加载时现转用的。文档建议优先用离线量化。
  • KV cache 量化：--kv-cache-dtype，可选 fp8_e4m3、fp8_e5m2 等。
  • Speculative decoding：文档 advanced_features/speculative_decoding。--speculative-algorithm 可选 EAGLE3、EAGLE、STANDALONE（小草稿模型）、NGRAM 等；配套参数有 --speculative-draft-model-path、--speculative-num-steps、--speculative-num-draft-tokens、--speculative-eagle-topk。文档提醒在重叠调度下要显式设 --speculative-eagle-topk 1。
  • CUDA graph：--cuda-graph-config，或者按阶段的 --cuda-graph-max-bs-decode 等。
  • 注意力算子：文档 advanced_features/attention_backend。--attention-backend，以及 --prefill-attention-backend、--decode-attention-backend。
