推理 Infra · 第 5 课 / 共 9 课

把语法变成一张掩码

模型输出的是概率，解析器要的是一个字符都不能错的 JSON。这一课讲推理引擎怎样在采样的那一刻把不合法的 token 全部排除，这张「掩码」是怎么算出来的、算它要花多少、放在主循环的哪里，以及工具调用是怎样建在这套机制上面的。Agent 的每一次工具调用都要过这一关。

图里的概率、词表和 token 切分都是为了讲清机制编的小例子。引擎的行为、参数名和文件路径对照了两个项目当前的 main 分支。

1 · 采样前的一步

把不合法的 token 的概率清零

第 1 课讲过，模型每一步输出一个长度等于词表大小的 logits 向量，softmax 之后是每个 token 的概率，再从中采样。模型没有任何机制保证采到的 token 能让输出继续保持合法的 JSON：它只是觉得某些 token 更可能。提示词写得再清楚，也只是把合法输出的概率推高，到不了 100%。

约束解码（constrained decoding）在 logits 和采样之间插入一步：根据已经输出的内容和目标语法，算出此刻哪些 token 是合法的，把其余 token 的 logit 设成负无穷。softmax 之后它们的概率正好是 0，合法 token 的概率按原来的比例自动放大到总和为 1。这张标明每个 token 合法与否的表就是掩码（mask）。

下图用一个很小的例子走一遍。目标是让模型按这个 schema 输出：city 是三个城市之一，days 是整数。

预测这个例子里，模型每一步选到合法 token 的概率都不低于 95%。不加约束，10 个 token 全部合法的概率大约是多少？

79%。每一步的合法概率相乘：0.96 × 0.99 × 0.995 × 0.95 × 0.99 × 0.995 × 0.97 × 0.97 × 0.98 × 0.97 ≈ 0.79。

输出越长、结构越复杂，要连续做对的步数越多，这个乘积掉得越快。约束解码把它直接变成 100%，代价是每一步多算一张掩码。

走完图 1 还能看到一件事：10 个 token 里有 7 个是语法唯一确定的，模型真正在做选择的只有城市、天数和要不要再写一位数字这三处。第 4 节会回到这一点。

2 · 掩码怎么算

语法按字符定义，模型按 token 输出

难点在于两边的单位对不上。JSON 的语法规则是逐字符写的：左花括号后面要么是引号要么是右花括号。模型的词表里是 token，一个 token 可能是半个词，也可能是 "," 这样一口气跨过「字符串结束、逗号、下一个字符串开始」三个语法位置的片段。

所以算掩码要做的事情是：把语法编译成一台按字符前进的自动机；对词表里的每一个 token，从自动机当前的状态出发，把这个 token 的字符一个个喂进去，中途走不通就是不合法，全部走通就是合法。

下图是一台只认「合法 JSON 对象」的小自动机（为了简单，不允许空白）。选一个已经输出的前缀，看 21 个 token 各自的命运。

预测「值写完了」这个位置上，token }} 合法吗？

看嵌套了几层。只有一层对象时，第一个 } 已经把整个 JSON 闭合了，第二个无处可去；嵌套两层时两个都用得上。在图 2 里切换「一层对象」和「两层对象」可以看到这一位从 0 变成 1。

这说明只记「语法走到哪条规则」不够，还得记一个栈。能用有限个状态描述的语法（正则表达式）可以把每个状态的掩码全部提前算好；JSON 这种能任意嵌套的语法需要带栈的自动机，状态有无穷多个，没法全部预先算。各家库的差别主要就在怎么处理这件事。

三种算法路线

朴素做法是每一步把十几万个 token 都走一遍，这在 Python 里要几十毫秒，比一次前向还慢。实际用的库各有各的省法：

做法编译（第一次见到这个 schema）每步算掩码
Outlines把约束变成有限状态机，提前为每个状态算好掩码慢，状态多时占内存查表
XGrammar带栈的字符级自动机。大部分 token 的合法性只取决于当前规则位置，提前算好；少数像 }} 这样取决于栈的 token，运行时再查通常很快，复杂 schema 可能到秒级微秒级
llguidance不做预计算。把词表组织成前缀树，每步在树上走一遍，共享前缀的 token 一起判定几乎没有文档给的数字是 128K 词表下约 50 微秒，少数情况到毫秒

两个引擎都把这些库当作可替换的后端。vLLM 默认是 auto，按请求内容在 xgrammar、guidance 等之间选；SGLang 用 --grammar-backend 指定。schema 先被转成语法（JSON Schema、正则、EBNF 都可以作为输入），再交给后端编译。

3 · 放进主循环

掩码在 CPU 上算，前向在 GPU 上跑，两件事同时做

把第 4 课的主循环拿过来，约束解码往里加了四件事：

  • 编译：请求刚到时把 schema 编译成自动机。这一步可能很慢，两个引擎都把它丢到线程池里做，请求先在一个专门的状态里等（vLLM 是 WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR，SGLang 是 grammar_queue），不挡主循环。编译结果按 schema 内容缓存，同一个 schema 第二次来直接命中。
  • 算掩码：每一轮为每个受约束的序列算一张掩码，在引擎进程的 CPU 上。
  • 应用掩码：掩码送到 GPU，对 logits 做一次按位操作。开销可以忽略。
  • 推进状态：采样出 token 之后，告诉自动机「走了这个 token」，它才知道下一步的状态（代码里叫 accept_token）。

这里有一条依赖链：第 N+1 步的掩码要等第 N 步采样出的 token。看起来这会打断第 4 课说的重叠调度，实际没有，因为两个引擎都把前向和采样拆成了两步。前向只需要上一个 token 作为输入，这个 token 一直留在 GPU 上，不用等 CPU；CPU 这边在前向进行的同时拿到上一步的 token、推进自动机、算出新掩码，前向一结束就拿掩码去采样。只要算掩码比一次前向快，它就完全藏在前向的时间里。

预测默认参数：128 个序列全部受约束，每张掩码 50 微秒，单线程。约束解码让每一轮慢了多少？

没有变慢。128 张掩码一共 6.4 ms，一次前向要 71 ms，掩码在前向跑到十分之一的时候就算完了。

把掩码耗时拖到 1 ms 以上再看：128 ms 的掩码时间超过了前向，GPU 开始等 CPU。这时有三条路：换更快的后端、加线程、或者接受吞吐下降。把线程数切到 8，等待又消失了。llguidance 的文档里有一句同样意思的话：16 个核、前向 10 ms 时，它可以在不拖慢模型的前提下支撑 3200 的 batch。

再切到「快 4 倍」的模型：前向变短，同样的掩码耗时更容易露出来。和第 4 课的结论一样，模型越快，CPU 上的活越要紧。

开销清单

  • 第一次编译是最显眼的一项。vLLM 的工具调用文档直接写着：第一次使用会有几秒甚至更长的延迟，之后走缓存。它只影响这个请求自己的首 token 延迟，不影响别人。
  • 每步掩码的总量和受约束的序列数成正比。vLLM 在一轮里受约束的请求超过 128 个时，会把它们按 16 个一组分给线程池并行算，线程数最多 8 个。
  • 和其他功能的交互。第 6 课要讲的 speculative decoding 一次猜好几个 token，自动机就得能试走几步再退回来（rollback）。SGLang 在语法约束遇上某些猜测算法时会放弃重叠，先处理完上一轮再排下一轮。
4 · 反过来省时间

语法已经确定的 token，可以不问模型

图 1 里有 7 步，语法只允许一种写法：schema 规定了属性名和顺序，{"city":" 这一串字符在请求到达时就已经确定了。为这些 token 各跑一次前向是浪费，掩码把词表削得只剩一个 token，模型算出来的概率分布根本没用上。

所以可以反过来利用语法：发现接下来的一段只有一种合法写法时，直接把这段文字接到输出后面，跳过这几步的采样。SGLang 的论文把它叫 jump-forward，llguidance 叫 fast-forward tokens，XGrammar 提供了 find_jump_forward_string。对属性名很长、值很短的 JSON，能省掉大半的 decode 步数。

它有一个细节要处理好：这段确定的文字要重新分词，而分词结果要和模型自己会输出的切法一致，否则后面的 KV 是在一个模型没见过的 token 序列上算的，质量会下降。服务路径里是否默认启用，取决于引擎版本和所选的后端。

5 · 工具调用

工具调用是「模板 + 解析器 + 可选的语法约束」

模型本身没有「调用工具」这个动作，它只会输出文本。工具调用在推理引擎这一层由三段拼成：

  1. 进：请求里的 tools（每个工具的名字、说明、参数的 JSON Schema）由 chat template 拼进 prompt。这就是第 4 课图 1 第 2 步里说的「工具定义被拼进 prompt」。
  2. 模型输出：模型训练时学过一种约定的写法。比如 Hermes 风格是把一段 JSON 包在 <tool_call> 标记里，Llama 3 是直接输出一个 JSON 对象，还有模型用 Python 函数调用的写法。每家不一样。
  3. 出：引擎前端的工具解析器（tool parser）认出这种写法，把它从文本里摘出来，转成 OpenAI 协议里结构化的 tool_calls 字段。启动服务时要用 --tool-call-parser 告诉引擎用哪一种。

解析器跑在第 4 课说的前端进程里，在反分词之后。流式输出时它要边收边判断：这段文字是正文，还是工具调用的一部分？函数名读完了没有？下图走一遍。

什么时候有语法约束

这是最容易想当然的地方。解析器只负责「摘出来」，不负责「保证能摘出来」。模型输出的 JSON 少了一个引号，解析器就摘不出合法的参数。要不要用第 1 到 3 节的机制去约束模型的输出，由 tool_choice 和工具定义里的 strict 字段决定。下表是 vLLM 文档里的规则，SGLang 的实现是同一套思路。

tool_choice模型的义务有没有语法约束
"auto"（默认）可以调用，也可以直接回答默认没有。至少一个工具写了 strict: true，或者服务端设了 --tool-strict-level，才有
"required"至少调用一次有
指定某个函数调用这个函数有
"none"不调用不涉及

auto 模式下的约束有个特别之处：模型可以先自由地说话，也可以完全不调用工具，语法不能从第一个 token 就管起来。这靠一种叫 structural tag 的语法形式实现：平时不约束，一旦输出里出现触发标记（比如 <tool_call>），从那里到结束标记之间按语法约束。图 4 切到「工具写了 strict」可以看到约束是从哪个 token 开始的。

约束还分两层。外壳（标记和函数名）只要 structural tag 生效就会约束；每个工具的参数 schema 只有该工具写了 strict: true 才会逐字段约束，否则参数只保证是合法的 JSON。服务端可以用 --tool-strict-level function 或 parameter 把所有带工具的请求统一抬到某一层，不依赖客户端有没有写 strict。vLLM 文档里有一句提醒：大多数 agent 框架从不设置 strict，所以默认情况下工具调用是没有语法保护的。

预测开了约束，同时设了 max_tokens=20。输出一定是合法的 JSON 吗？

不一定。语法约束保证的是「已经输出的部分总能被续写成合法的 JSON」，不保证它在长度用完之前写完。第 20 个 token 时对象还没闭合，得到的就是半截 JSON，finish_reason 是 length。

harness 这一侧要检查 finish_reason，给工具调用留够 max_tokens。

6 · 边界

约束保证不了的事

  • 只保证语法，不保证内容。文档的原话是：保证得到一个能解析的函数调用，不保证是一个高质量的。城市名在枚举里，不代表它是用户问的那个城市。
  • 会被截断。上面测验里说的 max_tokens。
  • 掩码改变了模型原本想说的话。模型想先解释一句再给 JSON，被掩码强行按进 JSON 里，它后面的选择是在一个自己没打算走的开头上做的，质量可能下降。两条常用的对策：在 prompt 里也把 schema 讲清楚，让模型本来就想这么输出，约束只负责兜底；需要推理的任务，在 schema 里把推理字段放在答案字段前面，因为属性是按顺序生成的。
  • 思考过程默认不受约束。带推理的模型，约束从思考结束之后才开始生效。vLLM 里对应 reasoning_ended 这个状态，配置项 enable_in_reasoning 默认是关的。
7 · Agent 视角

错误率是按步数连乘的

聊天里一次格式错误，用户重试一下就过去了。Agent 一个任务要连续调用几十次工具，任何一次参数解析失败都要 harness 处理：重试、把错误喂回给模型、或者整个任务失败。每一种都要多花 token 和时间。

服务端兜底比指望客户端可靠。harness 和 agent 框架通常用默认的 tool_choice="auto"，也不写 strict，这时工具调用没有语法约束。自己部署推理服务时，可以用 --tool-strict-level 在服务端统一打开。

工具定义要稳定，有两个缓存靠它。第 3 课讲过工具定义在 prompt 的最前面，顺序一变前缀缓存就失效。这一课多了一个：语法的编译结果是按 schema 内容缓存的，工具集合或 schema 文本变了就要重新编译。动态增删工具的 harness 两头都吃亏。

第一次调用的延迟要预热掉。复杂 schema 的首次编译可能是秒级的，落在某个用户的首 token 延迟上。服务上线后先用真实的工具定义发一轮请求，把编译缓存填上。

工具多了，三处一起变重。几十个工具的 schema 拼进 prompt，前缀变长（第 3 课），分词和模板渲染变慢（第 4 课），要编译的语法变大（本课）。按任务阶段只暴露用得上的工具能缓解，但要和上一条「工具定义稳定」权衡。

8 · 对应到真实系统

源码入口和开关

路径以当前 main 分支为准。

vLLM

  • 总入口：vllm/v1/structured_output/__init__.py 的 StructuredOutputManager。grammar_init() 提交编译，grammar_bitmask() 算一轮的掩码，accept_tokens() 推进自动机。
  • 后端：同目录的 backend_xgrammar.py、backend_guidance.py、backend_outlines.py。
  • 在主循环里的位置：vllm/v1/engine/core.py 的 step()，顺序是 execute_model()（不等结果）→ scheduler.get_grammar_bitmask() → sample_tokens(grammar_output)。推进自动机在 Scheduler.update_from_output() 里。
  • 工具解析器：vllm/tool_parsers/，每种模型格式一个文件，比如 hermes_tool_parser.py。
  • 请求参数：response_format，或者 structured_outputs 里的 json、regex、choice、grammar、structural_tag。旧的 guided_json 一类字段已在 v0.12.0 移除。
  • 服务端开关：--enable-auto-tool-choice、--tool-call-parser、--tool-strict-level、--structured-outputs-config.backend。环境变量 VLLM_XGRAMMAR_CACHE_MB（默认 512）限制编译缓存的大小。

SGLang

  • 后端基类：python/sglang/srt/constrained/base_grammar_backend.py。BaseGrammarBackend 里有编译用的线程池和按（类型，内容）做键的 cache。
  • 后端：同目录的 xgrammar_backend.py、llguidance_backend.py、outlines_backend.py。
  • 等编译的队列：constrained/grammar_manager.py 的 GrammarManager.grammar_queue，编译好的请求由 get_ready_grammar_requests() 放回等待队列。
  • 每轮算掩码：sampling/sampling_batch_info.py 的 update_regex_vocab_mask()。重叠模式下推迟的采样在 scheduler.py 的 launch_batch_sample_if_needed()。
  • 工具调用：function_call/function_call_parser.py，各模型格式在同目录的 *_detector.py。
  • 开关：--grammar-backend、--tool-call-parser。环境变量 SGLANG_TOOL_STRICT_LEVEL 对应 vLLM 的 --tool-strict-level。
