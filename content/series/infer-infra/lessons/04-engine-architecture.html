推理 Infra · 第 4 课 / 共 9 课

一个请求经过的进程和队列

前三课讲的调度、分页、前缀缓存，都发生在引擎最里面的那个循环里。这一课往外退一步看整台服务：请求怎样从 HTTP 进来，变成 token id，排进调度器，再变回文字流出去。重点有两个：两个引擎各把这些工作分给了哪些进程，以及 CPU 上的开销怎样让 GPU 空等。

函数名和文件路径都对照了两个项目当前的 main 分支。图里的耗时数字是示意，沿用第 1 课的成本模型。

1 · 请求的一生

从 JSON 到张量，再回到文字

客户端发来的是一段 JSON，GPU 要的是整数张量，客户端最后收到的又是文字。中间要做四次转换，全部在 CPU 上：

  • 渲染 chat template：模型自带一段模板，把 messages 列表（还有工具定义）拼成它训练时见过的那种带特殊标记的字符串。
  • 分词（tokenize）：把字符串切成 token id 序列。
  • 反分词（detokenize）：把模型吐出的 token id 变回文字。
  • 流式写出：用 SSE（Server-Sent Events）发给客户端。SSE 就是一个不关闭的 HTTP 响应，服务器每有一点新内容就往里写一行 data: {...}。

夹在中间的才是调度和前向计算。下图把一个流式聊天请求走过的每一站按顺序画出来：竖线是进程，横向箭头是跨进程的消息，方块是在某个进程里做的一件事。可以切换两个引擎对比。

两个引擎怎么分工

事情是同一批，分法不同。最显眼的两处差别：反分词放在哪，以及前向计算由谁发起。

ZMQ 是一个消息队列库，这里只用来在同一台机器的进程之间传消息。跨进程就得把对象序列化成字节再还原，所以两个引擎在进程之间传的都是 token id 这类紧凑的数据，文本只在最外层出现。

预测第 3 课里，Agent 第 30 步的请求有 99% 的 prompt 命中前缀缓存。图 1 的哪些步骤没有因此变快？

GPU 之前的所有步骤。模板渲染和分词每次都对整个 prompt 做一遍，全部 token id 都要序列化后送进引擎，调度器查前缀缓存也要把整个 prompt 走一遍（vLLM 逐块算哈希，SGLang 沿 radix tree 逐段比对）。

前缀缓存省的是 GPU 上的 prefill。CPU 上这些和上下文长度成正比的开销还在，GPU 那边省下来之后，它们在首 token 延迟里的占比反而上升。

第 1 课的等待队列和 token 预算、第 2 课的块分配和抢占、第 3 课的前缀查找，全部发生在「决定这一轮跑谁」这一行里。第 2 课说的「请求结束时归还块」发生在「记账」这一行。

有一处行为不同。vLLM 的一轮里 prefill 和 decode 的 token 混在同一个 batch 中，受同一个 token 预算约束。SGLang 默认每轮只跑一种：get_next_batch_to_run() 先看能不能从等待队列组出一批新请求做 prefill，组得出就跑这批，组不出才让正在运行的请求做一轮 decode；上一轮 prefill 完的请求会并入运行中的 batch。想让两种混跑，要加 --enable-mixed-chunk。

3 · 为什么要拆进程

CPU 忙的时候，GPU 在空等

两个引擎都是 Python 写的。标准的 Python 解释器有一把全局解释器锁（GIL）：一个进程里不管开多少线程，同一时刻只有一个线程在执行 Python 代码。所以只要分词、反分词、拼 JSON、写 SSE 和调度循环待在同一个进程里，它们就得轮流用 CPU。

GPU 的前向计算本身不占这把锁，但发起下一次前向要靠调度循环。循环被别的 Python 代码占着，下一轮就发不出去，GPU 就闲着。一块几万美元的卡在等一段字符串拼接。

解决办法分两步。第一步把和请求数成正比的前端工作搬到别的进程，那里有自己的 GIL。第二步让调度和前向重叠：GPU 算第 N 轮的时候，CPU 已经在排第 N+1 轮。下图把三种做法放在同一条时间轴上。

预测保持默认参数，把模型换成「快 4 倍的小模型」。A 和 C 的 GPU 利用率差距会变大还是变小？

变大很多。标准速度下 A 是 82%，C 是 100%。换成小模型后 A 掉到 53%，C 还是 100%。

CPU 上的开销和模型大小无关：调度还是 3 ms，前端还是每轮 12.8 ms。GPU 每轮从 71 ms 缩到 18 ms，CPU 那部分的占比就从不到两成涨到接近一半。模型越快、GPU 越强，CPU 侧的架构越重要。两个项目这几年在这上面的重构，动机都在这里。

再看小模型下 C 的前端负载：72%。把并发拉到 512、前端每 token 耗时调到 0.12 ms，它会超过 100%，这时该加前端进程了。

这三种架构对应什么

  • B 是两个引擎现在的基本形态。vLLM 的 API server 和 EngineCore 是两个进程；SGLang 更进一步，把反分词也单独拆了出去。
  • C 在两边都是默认开启的。SGLang 叫 overlap schedule，对应 event_loop_overlap()：发起第 N 批的前向后不等结果，回头去处理第 N−1 批的结果。可以用 --disable-overlap-schedule 关掉。vLLM 叫 async scheduling，文档的说法是 GPU 跑第 N 步时 CPU 调度第 N+1 步，对应 AsyncScheduler，可以用 --no-async-scheduling 关掉。
  • 重叠有代价。排第 N+1 轮时，第 N 轮的结果还没出来，调度器只能先假设每个请求都会继续。刚好在第 N 轮结束的请求会在下一轮多占一个位置，多算的那个 token 被丢掉。语法约束看起来和重叠冲突，因为下一步的掩码要等上一个 token。两个引擎的办法是把前向和采样拆开：前向照常提前发起，只有采样等掩码算好再做，第 5 课细讲。

前端跟不上时，后果在 A 和 B/C 里完全不同。A 里前端的活直接挡住下一轮前向。B/C 里 GPU 照常跑，输出在前端排队：vLLM 的 RequestOutputCollector 会把同一个请求积压的多个输出合并成一个再交出去，客户端看到的流变成一顿一顿的，延迟变差，吞吐不受影响。

4 · 输出这一侧

token 不能一个一个单独变回文字

反分词看起来是查表，其实要带状态，原因有两个。

第一，一个字符可能被切成几个 token。表情符号和生僻字在词表里没有整块的条目，会被拆成字节级的 token，只拿到前一半时解码出来是乱码字符 �。所以反分词器要记住每个请求「已经解码到哪、已经发出到哪」，遇到不完整的字符先扣住。

第二，stop 字符串。客户端可以指定一些字符串，输出里一出现就停止生成。它是按文字匹配的，可能横跨好几个 token，模型吐出前半截时还不能确定是不是它。已经发给客户端的字收不回来，所以只能先扣住一段。

预测不设 stop 时，句号在第 5 步发出。设了 "\n\nUser:" 之后，它在第几步发出？

第 7 步，晚了两个 token。这个 stop 串有 7 个字符，vLLM 始终扣住末尾 6 个。第 5 步文本一共才 5 个字符，一个都发不出去；第 6 步有 7 个字符，放行 1 个；第 7 步有 11 个字符，放行到第 5 个，句号才出去。

所以 stop 串越长，流式输出滞后得越多。滞后的只是「发出」，生成速度没有变。

在真实系统里

  • vLLM 的反分词和 stop 匹配都在 API server 进程的 OutputProcessor 里。stop 串匹配成功时，引擎那边并不知道，要由 API server 再发一条中止消息回去（代码里的 reqs_to_abort）。这条消息到达之前引擎可能已经又跑了一两轮，多出来的 token 被丢弃。EOS 和 max_tokens 不同，它们按 token 判断，调度器在记账时当场就知道。
  • SGLang 的 stop 串检查放在 Scheduler 进程里（Req 对象解码输出的末尾一小段来比对），所以引擎自己就能停，不需要绕一圈。Detokenizer 进程用 DetokenizeState 记每个请求的偏移量，负责扣住不完整的字符，并用 trim_matched_stop() 把 stop 串裁掉。
  • 两边都有 --stream-interval，默认是 1，即每个 token 发一次。调大后攒够几个 token 才发一次，流没那么顺滑，换来前端开销下降。它直接对应图 2 里「前端每 token 耗时」那个滑块。
5 · 取消

客户端走了，GPU 要尽快知道

请求在三个进程里都留了状态：前端有连接和输出队列，引擎有调度状态和 KV 块。客户端中途断开时，这些都要清掉，否则 GPU 会继续为一个没人看的请求生成，占着 batch 位置和显存。取消消息走的是图 1 的输入方向。

  • vLLM：连接断开时，处理这个请求的协程被取消，AsyncLLM.generate() 捕获到 asyncio.CancelledError，调 abort()，先清前端的状态，再给 EngineCore 发一条 ABORT。EngineCore 把它放进单独的 aborts_queue，在每轮 update_from_output() 之前处理，等前向结果的间隙里也会处理。最终落到 scheduler.finish_requests()，把请求标成 FINISHED_ABORTED 并归还 KV 块。
  • SGLang：主进程在每发完一个 chunk 后、以及等输出超时的时候检查 request.is_disconnected()，发现断开就调 abort_request()，给 Scheduler 发一条 AbortReq。Scheduler 把还在排队的请求直接删掉；正在运行的请求被标记为结束，按源码注释，它还会再跑一次 decode 前向，然后走正常的结束流程释放 KV。
预测取消一个正在 decode 的请求，它占的 KV 块最快什么时候能给别人用？

最快也要等当前这一轮前向结束。取消消息到达引擎时，这一轮的 batch 已经在 GPU 上算了，里面有这个请求的一行，没法中途抽走。这一轮结束后调度器处理取消、归还块，下一轮别的请求才能用。

再加上发现断开和跨进程传消息的时间，实际延迟是一到几轮。一轮几十毫秒，对单个请求无所谓；但如果取消很频繁、每次又都占着几万 token 的 KV，这段延迟里的显存就不能忽略了。

6 · Agent 视角

Agent 负载让哪几站变重

聊天负载下，图 1 里 CPU 上的那些步骤基本可以忽略。Agent 负载把其中几项放大了。

分词和模板渲染不吃前缀缓存。Agent 每一步都把完整的历史再发一遍，几十个工具的 JSON schema 也每次都要拼进 prompt。前缀缓存让 GPU 只算新增的部分，CPU 上这两步默认仍是对全文做。上下文到十万 token 时，单次分词粗略估计在百毫秒量级，这段时间直接计入首 token 延迟，而且占着前端进程的 CPU。

取消是常态。用户打断、harness 给工具调用设超时、并行跑几个子 agent 后只留一个结果，都会产生取消。每个被取消的请求背后是几万 token 的 KV，第 5 节的那条路径走得快不快，决定这些显存多久能回到池子里。

工具调用的输出不一定要逐 token 流式。harness 要等参数 JSON 完整了才能执行工具，中间的每个 token 对它没有用。这类请求可以不开流式，或者把 --stream-interval 调大，省掉前端按 token 计的开销。面向人的最终回答再用逐 token 流式。

子 agent 并发让前端先到瓶颈。一个任务同时开十几个子 agent，每个都带长上下文，前端要同时做十几份长 prompt 的分词。图 2 里的「前端负载」会先于 GPU 打满。这时该调的是 --api-server-count 或 --tokenizer-worker-num，加 GPU 没有用。

7 · 对应到真实系统

源码入口和开关

顺着图 1 的顺序列出。两个项目重构都很频繁，路径以当前 main 分支为准。

vLLM

  • HTTP 入口：vllm/entrypoints/openai/api_server.py。聊天接口的处理在 entrypoints/openai/chat_completion/serving.py 的 OpenAIServingChat。
  • 前端和引擎的接口：vllm/v1/engine/async_llm.py 的 AsyncLLM，看 add_request()、generate() 和 output_handler。
  • 输入输出处理：同目录的 input_processor.py、output_processor.py、detokenizer.py。
  • 跨进程通道：core_client.py 的 AsyncMPClient。
  • 引擎主循环：core.py 的 EngineCoreProc.run_busy_loop() 和 EngineCore.step()。
  • 执行器：vllm/v1/executor/ 下的 uniproc_executor.py（单卡）和 multiproc_executor.py（多卡）。前向在 vllm/v1/worker/gpu/model_runner.py 的 GPUModelRunner。
  • 文档 Design → Architecture Overview 给了进程数的算法：API server 数 + 引擎数 + GPU worker 数。例子是 4 卡张量并行共 6 个进程。
  • 开关：--api-server-count、--stream-interval（默认 1）、--no-async-scheduling。环境变量 VLLM_V1_OUTPUT_PROC_CHUNK_SIZE（默认 128）控制输出处理每处理多少个请求让出一次事件循环。

SGLang

  • HTTP 入口：python/sglang/srt/entrypoints/http_server.py。聊天接口在 entrypoints/openai/serving_chat.py 的 OpenAIServingChat。
  • 进程是怎么拉起来的：entrypoints/engine.py 的 _launch_subprocesses()。
  • 主进程一侧：managers/tokenizer_manager.py 的 TokenizerManager，看 generate_request()、handle_loop()、abort_request()。
  • 引擎主循环：managers/scheduler.py 的 event_loop_normal() 和 event_loop_overlap()，两个函数都只有几十行，适合对照着读。
  • 前向：Scheduler 持有 managers/tp_worker.py 的 TpModelWorker，它再调 model_executor/model_runner.py。
  • 反分词：managers/detokenizer_manager.py 和 managers/incremental_detokenize.py。
  • 开关：--disable-overlap-schedule、--stream-interval（默认 1）、--tokenizer-worker-num、--detokenizer-worker-num（默认都是 1）、--enable-mixed-chunk。
