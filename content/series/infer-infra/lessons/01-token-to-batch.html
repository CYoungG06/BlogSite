从一个 token 到一个 batch

一个 LLM 请求在 GPU 上经历了什么：为什么要有 KV cache，prefill 和 decode 为什么是两种不同的负载，vLLM 和 SGLang 为什么都用 continuous batching。后面讲显存分页、前缀缓存、调度器时要用的概念，这一页先备齐。

每张图都可以操作。标着「预测题」的地方请先自己想一个答案再展开。页面里的耗时来自一个简化的成本模型，数量级合理，但不是任何硬件上的实测值。

1 · 生成是一个循环

模型一次只回答一个问题：下一个 token 是什么

LLM 的一次 forward（前向计算）输入一串 token，输出一个概率分布，表示「下一个 token 是词表里每个词的可能性」。这个分布归一化之前的原始分数叫 logits。从分布里选出一个 token 的动作叫采样。

要生成一段话，就把采样出的 token 接到序列末尾，再 forward 一次，如此反复，直到采样出结束符 <EOS> 或达到长度上限。这叫自回归（autoregressive）生成。所以一个请求在 GPU 上是 1 次处理整段 prompt 的 forward，加上 N 次各产出 1 个 token 的 forward。

2 · KV cache

每一步只算新的那一行

Transformer 每一层的核心是注意力。每个位置的 token 在这一层会算出三个向量：Query、Key、Value。位置 i 的输出，是拿它的 Query 和各个位置的 Key 做点积得到一组权重，再用这组权重对各位置的 Value 加权求和。

生成式模型有一条硬规则，叫因果掩码（causal mask）：位置 i 只能看到 i 自己和它前面的位置。由此得到一个关键推论：前面位置的 Key 和 Value 不受后面 token 的影响。序列再往后接多少 token，它们的值都不变。

既然不变，就没必要每一步重算。把每一层、每个位置的 K 和 V 存起来，这就是 KV cache。新 token 进来时只算它自己的 Q、K、V，再用 Q 去读缓存里所有位置的 K、V。

图里只有 11 个 token，差距还不明显。换成 2000 token 的 prompt 加 500 token 的输出：有缓存时模型总共处理 2500 个 token；无缓存时是 2000 + 2001 + … + 2499，约 112 万个，相差约 450 倍。所以没有任何一个实用的推理引擎不带 KV cache，它是默认前提。

注意图 2 里第一步和后面各步的颜色不同。第一步一次处理整段 prompt，叫 prefill；之后每步只处理一个 token，叫 decode。这两个阶段的性质差别很大，第 4 节细讲。

预测题有了 KV cache，decode 每一步的耗时还会随序列变长而增加吗？

会，但增长很慢。新 token 的 Query 要和缓存里全部 t 个位置的 Key 打分，这部分随 t 线性增长（图 2 里橙色的那一行越来越长）。

而每层里的 MLP 和各种投影只针对这 1 个 token，与 t 无关，并且在常见长度下占大头。所以每步耗时近似常数，到上下文有几万 token 时，读缓存的开销才变得明显。

3 · 代价是显存

KV cache 用显存换计算，而显存是有限的

缓存要占地方。每个 token 在每一层都要存一份 K 和一份 V：

每 token 的 KV 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 每个数的字节数 Llama-3.1-8B (fp16) = 2 × 32 × 8 × 128 × 2 B = 131,072 B = 128 KiB

每个 token 128 KiB，8K 上下文的一条序列就是 1 GB。公式里的「KV 头数」值得留意：早期模型每个注意力头各有一组 K、V（Llama-2-7B 是 32 组）；现在的主流模型用 GQA（grouped-query attention），让多个 Query 头共用一组 K、V（Llama-3.1-8B 是 32 个 Query 头共用 8 组），KV cache 直接缩小到四分之一。

权重放进去之后，剩下的显存几乎全是 KV cache 的地盘。「并发数 × 上下文长度」被这块空间卡死，它直接决定一台机器能同时服务多少请求。把模型切到 Llama-2-7B 可以看到没有 GQA 时这个上限缩水多少。

预测题为什么不给每个请求按「最大上下文长度」预留一整块连续的 KV 空间？

因为请求最终会生成多长，事先不知道，而大多数请求远远用不满上限。按上限预留，大部分空间是空的，能同时服务的请求数被白白压低。

vLLM 论文测过当时的系统：KV 显存里真正存着 token 状态的只有 20%–38%。解决办法是像操作系统管内存那样分页、按需分配，这就是 PagedAttention，第 2 课的内容。

4 · 两种负载

Prefill 吃算力，decode 吃带宽

Prefill 把 prompt 的所有 token 放在一次 forward 里并行算。矩阵很大，GPU 的算力被吃满，耗时大致随 prompt 长度线性增长。它结束时产出第一个输出 token。

Decode 每步只算 1 个 token，计算量很小，但仍然要把全部权重从显存里读一遍。瓶颈变成了显存带宽，GPU 的算力大量闲着。8B 模型的 fp16 权重约 16 GB，高端 GPU 的显存带宽在每秒 2–3 TB 的量级，光读一遍就要 5–8 ms，这是单个请求 decode 每步耗时的下限量级。

衡量一个请求快慢的指标，就对应这两个阶段：

TTFT
Time To First Token。从请求到达到第一个 token 返回，等于排队时间加 prefill 时间。用户感受到的「反应快不快」。
TPOT / ITL
Time Per Output Token / Inter-Token Latency。相邻两个输出 token 的间隔。用户感受到的「吐字快不快」。TPOT 一般指平均值，ITL 指每一个间隔。
E2E 延迟
端到端耗时 ≈ TTFT + (输出 token 数 − 1) × TPOT。
吞吐
整个服务每秒产出的 token 数（所有请求加起来）。运营方关心的成本指标，和上面三个用户侧指标经常要互相交换。
和 Agent 的关系。Agent 每走一步，都把越来越长的历史（系统提示、工具定义、之前所有的调用和结果）整段重发，而输出常常只是一个简短的工具调用，输入输出比经常超过 100 : 1。时间和成本都压在 prefill 上。把「Agent 的一步」预设的缓存命中比例拖到 95% 看看 TTFT 的变化：让相邻两步共享前缀的 KV cache，是这类负载下最重要的一项优化。本页讲的 KV cache 只在一个请求内部复用，跨请求复用是第 3 课的前缀缓存。
5 · 为什么要攒批

Decode 时多带几条序列，几乎不要钱

上一节说 decode 每步的大头是「把权重读一遍」。这次读取可以被很多条序列共用：一个 batch 里放 B 条序列，权重还是只读一遍，每条序列各自多出的计算很少。所以 batch 从 1 加到几十，每步耗时只涨一点，总吞吐接近成倍增长。继续加大，每条序列自己的计算和读 KV cache 的开销逐渐成为主导，收益开始递减。

6 · 调度的粒度

从「一批请求」到「一轮迭代」

攒批划算，问题是怎么攒。请求不会整整齐齐同时到达，每条要生成多长也各不相同。

静态批处理是传统模型服务的做法：等凑够一批，或者等到超时，一起送进 GPU，一起跑到最长的那条结束，再接下一批。放到 LLM 上有三个问题：短请求早早结束，它的槽位却要空转到整批结束；新来的请求必须等当前这批跑完；请求稀疏时，凑批本身就在浪费时间。

Continuous batching（也叫 iteration-level scheduling，出自 Orca 论文）把调度的粒度从「一个请求」缩小到「一次 forward」。每一轮迭代开始前，调度器重新决定这一轮的 batch 里有谁：结束的请求立刻离开，排队的请求立刻补进来。

它带来一个新问题。一个长 prompt 的 prefill 混进 batch，这一轮迭代就会变得很长，同一个 batch 里正在 decode 的请求全都跟着卡一下。解法是 chunked prefill：给每轮迭代设一个 token 预算，decode 请求优先占用（每条只占 1 个），剩下的预算才分给 prefill，长 prompt 被切成几轮做完。

几个值得自己动手验证的现象：

  • 在 Continuous 模式下找一个输入 1500 以上的请求，看它 prefill 那一轮：同一列里其他请求的橙色格子被拉得很宽，这就是 prefill 对 decode 的干扰。切到 chunked 模式，宽格子变成几个中等宽度的格子。
  • 静态模式下，条纹格子是纯浪费。把并发槽位调大，浪费通常会更多，因为一批里长短差异更大。
  • 把 token 预算从 128 拖到 2048，观察表格里「最长 token 间隔」和「平均 TTFT」朝相反方向变化。
预测题把到达间隔拖到 300 ms 以上（请求很稀疏），静态批处理的 TTFT 和 Continuous 相比差距变大还是变小？

静态批处理仍然明显更差，而且原因变了。请求稀疏时凑不满一批，每个请求都要等到超时（这里设的是 100 ms）才开跑；如果到达时前一批还没结束，还要再等它跑完。

Continuous 模式下，只要槽位有空，请求到达后等当前这一轮迭代结束（20 ms 左右）就能进 batch。

预测题开启 chunked prefill 后，谁受益，谁受损？

正在 decode 的请求受益。它们的最长 token 间隔从「一整段 prefill 的时长」降到「一个 chunk 的时长」，输出更平滑。

长 prompt 自己受损。prefill 被切成多轮，每轮都要多付一次固定开销，TTFT 变晚。vLLM 文档对这个旋钮的描述也是如此：预算小，ITL 好；预算大，TTFT 好；追求吞吐时建议设到 8192 以上。

7 · 对应到真实系统

这些概念在 vLLM 和 SGLang 里叫什么

图 6 的模拟器是按 vLLM 的方式写的：prefill 和 decode 混在同一个 batch 里做一次 forward。两个引擎的调度循环结构不完全一样，读源码时可以从下面的入口开始。两个项目迭代很快，文件和参数以当前 main 分支为准。

vLLM

  • 调度入口是 vllm/v1/core/sched/scheduler.py 里的 Scheduler.schedule()，每调用一次，决定一轮迭代的内容。
  • 先安排所有正在 decode 的请求，预算有剩才安排 prefill。预算是 --max-num-batched-tokens，并发上限是 --max-num-seqs。
  • 当前版本（V1 引擎）默认启用 chunked prefill。
  • KV 显存不够时会抢占：把某个请求踢出去，默认做法是丢掉它的 KV cache，之后重新计算（RECOMPUTE）。

SGLang

  • 调度入口是 python/sglang/srt/managers/scheduler.py 里的 get_next_batch_to_run()。
  • prefill batch 和 decode batch 是分开的两次 forward：每轮先尝试从等待队列里组一个新的 prefill batch（逻辑在 schedule_policy.py 的 PrefillAdder），跑完后并入正在 decode 的 batch；没有新请求时就对现有 batch 跑一步 decode。
  • 相关参数：--max-running-requests、--chunked-prefill-size、--max-prefill-tokens、--mem-fraction-static。
  • 等待队列的排序策略可选（--schedule-policy）：当前默认是先来先服务，也可以选按「和缓存的最长公共前缀」排序的 lpm，第 3 课会讲。
