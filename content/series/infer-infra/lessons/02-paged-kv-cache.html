把 KV cache 切成页

第 1 课的结论是：显存里放完权重，剩下的都是 KV cache 的地盘，它决定一台机器能同时服务多少请求。这一课讲这块地盘怎么分。vLLM 的核心贡献 PagedAttention，就是把操作系统管理内存的办法搬到了 KV cache 上。

图里的显存池都缩小到了几百个 token 的规模，为的是一屏能看清每一格。机制和真实系统一致，数量不一致。

1 · 问题

一个请求要占多少显存，事先不知道

KV cache 每生成一个 token 就长一格，而一个请求最终会生成多少 token，要等它采样出结束符才知道。深度学习框架里的张量又要求一段连续的内存。两件事合在一起，早期的推理系统只能在请求进来时就给它划一整段连续空间，并且按可能的最大长度来划。

这样做有三种浪费：

  • 预留：划给这个请求、它之后确实会写到、但现在还空着的部分。空着的这段时间，别人用不了。
  • 内部碎片：划给了这个请求，但它到结束也写不到的部分。按最大长度预留时，大多数请求远远用不满。
  • 外部碎片：请求结束后留下大小不一的空洞。总的空闲空间够，但没有一段连续的空间够大，新请求还是进不来。

下面的模拟器里，同一组请求用三种办法分配显存。先看前两种连续分配。第三种「分页」是本课的主角，机制在第 2 节讲，讲完再回来切过去对比。

预测题「预知真实长度」已经没有内部碎片了，为什么池子还是用不满？

两个原因。一是预留：每个请求一进来就占住它最终需要的全部空间，其中大部分要过很多轮才写到。二是外部碎片：请求长短不一、结束时间不一，留下的空洞大小不一，后来的请求未必塞得进去。在模拟器里往后单步，会看到「空闲格数够，但最大连续段不够」的提示。

而且这个模式在现实中做不到，没人能预知输出长度。它是一个理论上界，用来说明连续分配再怎么优化也有限。vLLM 论文实测的三种连续分配基线里，KV 显存中存着真实 token 状态的比例分别只有 20.4%、26.8%、38.2%，最后一个就是预知长度的版本。

2 · 分页

不要求连续，问题就消失了

操作系统在几十年前遇到过同样的问题：每个进程要多少内存事先不知道，又都希望自己的内存是连续的。解法是虚拟内存加分页：把物理内存切成大小相同的页，进程看到的是连续的虚拟地址，实际的页散落在物理内存各处，中间靠一张页表翻译。

PagedAttention 把这套办法原样搬到 KV cache 上：

  • KV 池在启动时切成大小相同的物理块（block），每块放固定数量 token 的 K、V。
  • 每个请求有一张块表（block table），记录它的第 0、1、2… 个逻辑块分别放在哪个物理块。
  • 按需分配：上一块写满了，才去拿下一块。
  • 空闲的物理块排在一个空闲队列里，要用就从队头取，用完还到队尾。

三种浪费由此逐一消失：不再提前预留；内部碎片最多是最后一块里没写满的几格；所有块一样大，任何空闲块都能给任何请求用，外部碎片不存在。

和操作系统的概念逐一对应：

操作系统PagedAttention
进程一个请求（一条序列）
虚拟页逻辑块
物理页帧物理块
页表块表
按需调页上一块写满才分配下一块

注意力计算怎么读散落的块

每一层有一个大张量存这一层的全部 K、V，第一维就是物理块号。所以「一个物理块」实际上是每一层张量里同一个下标的那一片，分配一个块等于在所有层同时占住这个下标。算注意力时，引擎把每条序列的块表作为一个整数数组一起传给注意力算子，算子按块表逐块取出 K、V。这个能按块表取数的注意力算子，就是 PagedAttention 这个名字指的东西。

多一层间接寻址是有代价的。论文测到注意力算子本身比连续内存的高度优化实现慢 20%–26%，但只影响这一个算子，换来的是同一块显存能多放几倍的请求，论文报告的整体吞吐是当时系统的 2–4 倍。回到图 1 切到「分页」，看表格里「同时在跑」和「全部完成」几列的变化。

3 · 块的大小

一块放多少 token

块越小，最后一块里浪费的空间越少；块越大，块表越短，一次能连续读的数据越多。vLLM 默认每块 16 个 token。用第 1 课的数字算一遍（Llama-3.1-8B，48 GB 的 GPU，权重之外留给 KV 池约 28 GB）：

每 token 的 KV = 128 KiB （第 1 课算过） 每块 = 16 × 128 KiB = 2 MiB （跨全部 32 层） 物理块总数 = 28 GiB ÷ 2 MiB = 14,336 块 能缓存的 token 总数 = 14,336 × 16 = 229,376 每条序列最多浪费 = 15 个 token ≈ 1.9 MiB （最后一块只写了 1 格时） 32K 上下文的块表 = 2,048 个整数

vLLM 启动时会把这个结果打在日志里，形如 GPU KV cache size: 229,376 tokens, Maximum concurrency for 32,768 tokens per request: 7.00x。第二个数是「如果每个请求都用满最大上下文，能同时放几个」，是排查并发上不去时最先该看的一行。

在图 1 的分页模式下把块大小在 1、4、8、16 之间切换，观察条纹格子（最后一块里永远写不到的部分）的数量变化。

预测题块大小设成 1 就完全没有浪费了，为什么 vLLM 不这么做？

因为浪费本来就很小，而块太小有实际代价。每条序列最多浪费 15 个 token 的空间，相对几千上万 token 的序列可以忽略。

块大小为 1 时，块表长 16 倍，每个 token 都要单独寻址，算子读到的数据在显存里完全不连续。另外第 3 课会讲到，前缀缓存是以「写满的块」为单位做哈希和共享的，块太小管理开销大，块太大又难以命中。论文的消融实验里，块大小在 16 到 128 之间表现最好。

SGLang 走了另一条路：分配粒度可以细到单个 token，每个请求直接记录它每个 token 在池子里的下标。两种设计的对比见第 6 节。

4 · 共享

块表是间接的，所以两条序列可以指向同一块

有了块表这层间接，一个物理块可以同时出现在多条序列的块表里。只要给每个物理块加一个引用计数（有几条序列在用它），就能安全地共享。论文用它解决「同一个 prompt 采样多个回答」的场景：prompt 的 KV 只算一次、只存一份。

共享的块如果有人要往里写怎么办？和操作系统 fork 之后一样，写时复制（copy-on-write）。

这是论文里的机制。当前 vLLM（V1 引擎）的做法更简单：只共享写满的块，靠内容哈希来识别相同的块；块表只追加、不修改。写满的块不会再被写入，也就不需要复制；最后那个没写满的块不共享，由各条序列自己算。共享的收益几乎都在写满的块上，省掉复制逻辑换来实现简单。这套基于哈希的共享就是前缀缓存，第 3 课的主题。

5 · 用完了怎么办

抢占：乐观接纳的代价

按需分配意味着调度器接纳请求时是乐观的：只要够放下 prompt 就让它进来，不管它之后会长到多长。这让并发数高了很多，但也意味着可能出现所有请求都还在长、池子却空了的时刻。

这时必须有人让路，叫抢占（preemption）。vLLM 默认的做法是：

  • 选最后进来的那个在跑的请求作为牺牲者（默认的先来先服务策略下）。
  • 释放它的全部物理块，把它放回等待队列的队首。
  • 它已经生成的文本不丢，丢的是 KV cache。等它重新进来时，要把 prompt 加上已生成的部分重新 prefill 一遍。这叫 RECOMPUTE。
  • 发生抢占的这一轮不再接纳新请求，避免刚腾出的空间立刻又被占满。

论文里还描述了另一种做法：把被抢占请求的块换出到主机内存，之后再换回来（swap）。它省了重算，但要在 GPU 和 CPU 之间搬数据。当前 vLLM 默认用重算。

在图 1 的分页模式下播放，事件栏里带红色标记和 ✕ 的事件就是抢占。表格里「需重算的 token」是它的代价。

预测题为什么牺牲最后进来的请求，而不是占显存最多的那个？

占显存最多的往往是跑得最久、快要结束的请求。踢掉它，丢掉的 KV 最多，重算最贵，而它本来马上就会自己释放空间。

最后进来的请求做过的工作通常最少，重算代价最小。而且先来的请求永远不会被后来的挤掉，保证了先来先完成，不会有请求被反复抢占而饿死。

SGLang 的选择标准略有不同：优先撤回已生成 token 最少的请求，思路一样，都是让丢掉的工作最少。

抢占是安全网，频繁触发说明并发设得太高。vLLM 文档给的处理办法是：调高 --gpu-memory-utilization 给 KV 池更多空间，或者调低 --max-num-seqs、--max-num-batched-tokens 减少同时在跑的请求。

和 Agent 的关系。Agent 的一个会话，上下文常有几万到几十万 token，按每 token 128 KiB 算就是几 GB 到几十 GB 的 KV。更麻烦的是，会话在等工具返回的那段时间里，这些块不属于任何在跑的请求。留着它们，下一步可以直接接着用；让出去，别的请求能进来，但下一步要整段重算。分页、引用计数、空闲队列的顺序，正是回答这个问题的基础设施：一个请求结束后，它的块可以先留在空闲队列里不清空，直到真的被别人取走。这是第 3 课的起点。
6 · 对应到真实系统

两个引擎里的内存管理

两个引擎都不要求 KV cache 连续，都有一张从「请求里的位置」到「池子里的位置」的映射表，差别在粒度和数据结构。文件路径以当前 main 分支为准。

vLLM

  • 块管理在 vllm/v1/core/ 下：kv_cache_manager.py 是调度器调用的入口（allocate_slots()、free()），block_pool.py 管全部物理块，kv_cache_utils.py 里是数据结构。
  • 每个物理块是一个 KVCacheBlock，带 block_id、ref_cnt（引用计数）、block_hash（写满后才有，第 3 课）。全部块在启动时一次建好。
  • 空闲队列 FreeKVCacheBlockQueue 是一条双向链表，从队头取、还到队尾，能 O(1) 地从中间摘走一块。
  • 抢占逻辑在 sched/scheduler.py 的 schedule() 里：allocate_slots() 返回空时，取 self.running[-1] 调 _preempt_request()。

SGLang

  • 内存池在 python/sglang/srt/mem_cache/ 下。memory_pool.py 里的 ReqToTokenPool 是映射表：一个二维整数张量，每个请求一行，第 i 列是它第 i 个 token 在 KV 池里的下标。
  • 相当于块大小可以小到 1 的块表。没有内部碎片，代价是表更大、寻址更细。下标的分配器在 mem_cache/allocator/ 目录下。
  • 按 token 寻址和它的前缀缓存结构（radix tree，可以在任意 token 处分叉）是配套的，第 3 课会看到。
  • 显存不够时的对应机制叫 retract：schedule_batch.py 里的 retract_decode() 把一部分请求撤回等待队列。
